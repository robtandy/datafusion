# Native Parquet morsels: scan-to-pipeline handoff

This is the design handoff from [#131] to [#126] for the opt-in `morsel-execution` fork, not a change to Apache DataFusion's defaults or a proposal to replace `FileStream`. The datasource trace below is from the fork's upstream base, [`7e3d6516`]; the query pipeline comes from [#124]. Upstream [#20529] describes morsel-driven Parquet scanning, [#21598] distinguishes nonblocking morsels, and [#21719] and [#2226] provide scheduler context. Follow DuckDB's source/operator/sink split in the workspace reference checkout (`~/github/duckdb-morsel-reference/`, `9c1e4c5233af5953e6b35e88fbef5089eaace6e9`): `src/execution/physical_operator.cpp` separates source reads from sink/combine/finalize, `src/parallel/pipeline_executor.cpp` drives chunks through the pipeline, and `src/execution/operator/join/physical_join.cpp` and `src/parallel/executor.cpp` illustrate dependent pipelines. Reuse that lifecycle, not DuckDB's interfaces or event machinery.

## What the checkout does today

1. **Provider and file assignment.** [`SessionContext::register_parquet`] installs a `ListingTable` with `ParquetFormat`. The stock [`DefaultPhysicalPlanner`] resolves `TableScan::source`, strips qualifiers from scan filters and passes projection, filters, fetch, skip and statistics requests in `ScanArgs` to `TableProvider::scan_with_args`. [`ListingTable::scan_with_args_inner`] lists files, separates partition filters, collects configured statistics, assigns `PartitionedFile`s to `FileGroup`s and builds `FileScanConfig`. If no file groups remain, the provider can return a projected `EmptyExec`; a skip can wrap the scan in `GlobalLimitExec`. These are planning operations, including any listing or statistics I/O; they are not query worker morsels.
2. **Configured source.** [`ParquetFormat::create_physical_plan`] sets up `ParquetSource` with table options, the session object store, the cached reader factory, metadata size hints and any encryption configuration. It wraps the resulting `FileScanConfig` in `DataSourceExec` (inspect it with [`DataSourceExec::data_source`]). Physical filter pushdown happens separately: [`FileScanConfig::try_pushdown_filters`] unprojects expressions and remaps column indices to the table schema before calling [`ParquetSource::try_pushdown_filters`]. Even with row pushdown disabled, accepted candidates can populate `ParquetSource::predicate` for pruning; the returned `PushedDown::No` means the parent must still evaluate them. A predicate in the source or in `TableScan::filters` is not proof of row filtering.
3. **Stock execution.** [`FileScanConfig::open_with_args`] gets the store from `TaskContext`, sets the configured or session batch size and memory pool, calls `FileSource::create_morselizer(store, config, partition)` and builds a `FileStream`. [`ScanState`] drives its local file group or [`SharedWorkSource`] of unopened files. It polls at most one pending planner I/O future per stream and drains the active reader/ready morsels; it returns pending, not EOF, while there is outstanding I/O. Unordered sibling file stealing is not shared claiming of decode-ready work. [`ParquetSource::create_morselizer`] implements it directly; [`FileOpenerMorselizer`] is a legacy compatibility adapter, not a native seam.
4. **Parquet open and pruning.** [`Morselizer::plan_file`] consumes a file descriptor and returns a `MorselPlanner`. Its synchronous `plan(self)` returns `None` for an exhausted branch, or a `MorselPlan` with ready morsels, CPU-ready child planners, and/or one `PendingMorselPlanner`. The driver must poll the latter to obtain the next planner. [`ParquetMorselPlanner`] drives CPU-only setup and pruning transitions; metadata, optional page-index and bloom loads (and optional encryption setup) return pending futures. `prepare_filters` adapts projection and predicate to the per-file schema; `prune_row_groups` applies range and statistics restrictions. `build_stream` turns the surviving row groups into an access plan, applies page pruning and builds the decoder and projection mapping. A pruned file can finish without publishing a morsel.
5. **The missing handoff.** Today `build_stream` creates a `PushDecoderStreamState`; the planner emits one `ParquetStreamMorsel` for that resulting file/range stream. As [`PushDecoderStreamState::transition`] shows, polling it drives [`ParquetPushDecoder::try_next_reader`]. `NeedsData(ranges)` awaits `AsyncFileReader::get_byte_ranges` then calls `push_ranges`; `Data(reader)` yields a synchronous `ParquetRecordBatchReader` over the supplied data, and `Finished` ends that decoder. Batches are mapped through `DecoderProjection` to the scan schema. The current `ParquetStreamMorsel` therefore still awaits **data** I/O, even after **planner** I/O completed. The trait's [`Morsel`] contract (decode without I/O) is the goal, not evidence that this existing implementation meets it.

## Proposed seam for #126

Use a **buffered row-group reader** as the initial work unit, not a file stream, a DataFusion partition, a pending range request, or a batch already decoded by an I/O task.

- **Lower at the scan leaf.** In the fork's [`core/src/morsel.rs`][fork-morsel], admit a known Parquet `ListingTable` and call its normal provider scan planning with the optimized `TableScan`'s projection and unqualified filters. Extract and validate the resulting `DataSourceExec` → `FileScanConfig` → `ParquetSource` without executing any of them. Do not run the full stock physical optimizer and then strip wrappers: it may install a pushed limit, range split, exact filter or a metadata-only result. Reuse the scan's projected schema, file descriptors, reader factory and runtime configuration, and lower supported residual filters/projections in their original order. Distinguish a proven-empty admitted provider (`EmptyExec` from listing) from an arbitrary plan with no scan. An admitted empty source can use the same completion protocol without dispatching any readers. Gate this source on core's `parquet` feature. The current memory pipeline claims in-memory batch ranges and ignores `TaskContext` in `MorselExec::execute`; pass that context into the Parquet run to configure the morselizer (store, batch size and memory pool), and leave memory-source claiming intact.
- **Expose one alternate emission path in Parquet.** Factor the decoder/access-plan initialization out of [`RowGroupsPrunedParquetOpen::build_stream`] for reuse. Add an opt-in Parquet-specific morselizer constructor/mode that shares the setup in `ParquetSource::create_morselizer`; leave that trait method's stock behavior and the existing `PushDecoderStreamState` stream driver intact. After metadata/index/bloom planning, step the initialized push decoder on a CPU path. For each `NeedsData`, yield a pending planner that only fetches ranges and returns the continuation with its bytes; feed those bytes back on the next CPU step. One row group can require several such exchanges. On `Data(reader)`, return precisely one owning `Morsel` plus a ready continuation for the remaining decoder. The reader morsel carries the reader from the **push decoder**, shared immutable projection/schema state, and applicable metrics, not the `AsyncFileReader`. Its `into_stream` iterates and maps batches without opening files or requesting bytes. `Finished` produces no more work for that file. Do not assume every selected row group returns a reader or every reader emits rows. Keep file progress on the planner side and separate reader-level claim/decode metrics from file completion metrics.
- **Reuse the existing contracts.** [`MorselPlan`]'s `take_morsels`, `take_ready_planners` and `take_pending_planner` already convey the necessary transitions. Reuse `ParquetFileReaderFactory`/[`AsyncFileReader` plumbing][parquet-reader], metadata and access-plan pruning, `DecoderBuilderConfig`, `DecoderProjection` and the arrow-rs push decoder. Keep the experimental work driver in core; no change to `FileStream`, `ScanState`, the legacy adapter, listing, or the benchmark harness is required. If sharing `open_with_args` setup avoids divergence, extract only store/batch-size/pool preparation, not its stream state machine. Keep any cross-crate API narrowly marked experimental/internal to the workspace.

`try_next_reader` does CPU work to prepare the reader. Run this and metadata/pruning steps on a CPU-side producer, not on the I/O executor; workers perform the batch decode, mapping and operators. A separate Tokio runtime is optional; separation here means the I/O path polls pending futures and pipeline workers never await object-store requests. Do not prefetch whole files or implement another Parquet decoder just to make a queue entry nonblocking.

### Ownership, backpressure, and completion

| Owner                          | Responsibility                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider/planner               | Own file enumeration, logical projection and group assignment at plan time. After admission, group membership carries no distribution guarantee; it can still label metrics.                                                                                                                                                                                                                                                                                                                             |
| Per-execution scan driver      | Walk the admitted file groups once, lazily. Admit only a bounded number of active file planners, each with exclusive ownership of its decoder frontier. Plan surviving row groups once via the Parquet access plan; keep pending, runnable and published work distinct. Never recreate a planner from a file just because a worker becomes idle.                                                                                                                                                         |
| Async I/O path                 | Own and poll a bounded set of `PendingMorselPlanner`s (metadata/index/bloom **and** data), at most one outstanding per active file lane. Return each result or error to the driver, including continuations that produce no reader. No detached reads: dropping/aborting a run drops the futures (a store may still complete an already-issued remote request).                                                                                                                                          |
| Shared ready queue and workers | The queue owns each reader until one worker atomically removes it; a worker owns that reader until drained or cancelled. All workers can claim from the same queue, including readers from one file/stock group. They decode incrementally, apply operators and feed the bounded result sink or [#125]'s worker-local counters. No retries of partially consumed readers.                                                                                                                                |
| Run supervisor                 | Own child lifetimes, cancellation, and terminal status. On the first observed planning, I/O, decode, operator or sink failure, report the original error with context, stop admission, abort peers and drop queued work; do not let error publication wait behind a full result queue. Stream drop uses the same teardown, including tasks waiting on I/O or permits. Check cancellation/yield between batches and bounded planner steps; an already-running synchronous decode call is not preemptible. |

Set separate positive caps for active file lanes, in-flight planner futures and ready readers. For example, reserve a ready permit before a decoder step that can publish a reader, transfer it with the reader to the queue, and release it on claim; a worker may hold at most one claimed reader. Release the reservation on a step that yields only I/O or completes without a reader. A completed I/O future that cannot yet resume may park only in its existing lane slot. Do not stage extra readers in blocked senders or spawn a task per unopened file. When the sink stalls, bounded workers, queue and lanes limit further reads; counters should account for reserved and parked items as well as enqueued ones. These are **work-count** bounds: a single row group or range request can still be large, and a range request can fan out inside the store. Do not present queue capacity as a byte or HTTP request limit.

An empty ready queue means **wait** unless the driver has exhausted the file iterator and all active lanes/continuations (including completed I/O awaiting CPU), and no publisher can enqueue again. Wake on I/O completion, work publication, capacity release and termination, without spinning. Only then close ready input; workers drain queued/claimed work. Successful query EOF also waits for worker completion and any buffered results; for `COUNT(*)` it waits for combine and **one successful finalize** before the dependent result pipeline starts. Empty, fully pruned and zero-row readers use those same rules and can finalize to zero. Failure/cancellation is not successful EOF and must not publish a partial count. Reset all mutable claims, queues and counters for each execution of a prepared plan.

## Initial admission matrix

This is a conservative first slice, not the set of features supported by the stock Parquet reader. Check both the logical query and the configured scan; reject an unknown wrapper or feature before starting native execution.

| Feature                   | Admit in #126                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Reject or defer                                                                                                                                                                                                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Projection and schema     | File-column index projection (including reordered columns and zero-width batches where row counts are preserved); supported synchronous pipeline expressions/aliases. Keep aliases, field order, types, nullability and metadata. Keep residual predicate inputs in the scan output until the filter has run, even when the final `SELECT` or `COUNT(*)` does not use them. Plan/rebind expressions against the actual input at each operator. Use the existing per-file projection/schema adapter for supported casts and missing columns. | Anything requiring async/row-context expressions or a projection/schema mapping the adapter cannot preserve. Do not strip a predicate-only column or infer row count from the number of projected arrays.                                                                                                                       |
| Pruning versus filtering  | Use listing and static file/row-group statistics, optional bloom and page pruning according to scan options. The first slice uses **pruning-only** scan predicates and the optimized logical residual `Filter` for row semantics (`NULL` is not true). [`ListingTable::supports_filters_pushdown`] reports ordinary file predicates as `Inexact`; [`PushDownFilter`] retains their residuals. Use the scan copy only for pruning.                                                                                                           | Defer exact Parquet `RowFilter` pushdown, dynamic filters and exact provider filters. Do not drop a residual because a predicate appears in scan filters or pruning metrics. Reject a preconfigured source predicate with unknown/enforced semantics, or an optimized shape whose residuals/column mapping cannot be preserved. |
| Limit/offset              | No limit or skip.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Reject logical `LIMIT`/`OFFSET`, `TableScan::fetch`/`skip`, a configured `FileScanConfig::limit` or a limit wrapper. Stock behavior spans per-scan limits, Parquet limit pruning and global skip; a per-reader budget is not equivalent.                                                                                        |
| Ordering and distribution | Unordered rows, no required partition layout. Ordinary listing file groups are enumeration input only, regardless of group count or `target_partitions`; the outer pipeline can expose one unordered result partition with several workers.                                                                                                                                                                                                                                                                                                 | Reject `ORDER BY`/TopK, advertised file order or preserve-order flags, sort pushdown/reverse scans, declared hash/range distributions and operators depending on them. Do not advertise stock scan ordering/distribution after shared claiming.                                                                                 |
| File layout and I/O       | Whole, unsplit standard Parquet files over the configured store, multiple files and row groups, empty files and normal per-file metadata/schema adaptation. Keep file-level statistics, row-group selections derived by native pruning, and reader factory metadata caching.                                                                                                                                                                                                                                                                | Defer byte-range splits, externally supplied `ParquetAccessPlan`/row selections and opaque per-file extensions, external compression and custom/encrypted layouts not explicitly supported and validated. Do not strip a range or extension and scan the whole file.                                                            |
| Virtual/partition columns | Ordinary file columns only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Defer Hive/directory partition columns (including exact partition predicates), `TableSchema` virtual columns such as row number, and scan-context expressions such as `input_file_name()`. Check the table/source as well as the final projection.                                                                              |
| Metadata-only results     | Use metadata to **prune**, never to manufacture a positive count. Admit an actual scan with the [#125] ungrouped filtered `COUNT(*)` sink.                                                                                                                                                                                                                                                                                                                                                                                                  | Reject scan statistics requests and metadata-rewritten/scanless aggregate plans as native Parquet work. Stock [`AggregateStatistics`] can replace a scan/aggregate with a literal on a `PlaceholderRowExec`; that is not evidence of a source or sink run.                                                                      |

For pruning-only v1, clone the verified scan configuration with `ParquetSource::with_pushdown_filters(false)` and attach eligible supported static scan predicates using `FileScanConfig::try_pushdown_filters` with the session Parquet row-pushdown flag also disabled **in the local config passed to that call**. Adopt its updated source even when the parent result is `PushedDown::No`; keep the logical residuals either way. Build hints against the projected scan schema expected by the pushdown API, which handles the table-schema remap. If a hint's inputs are not available there, omit the hint rather than changing row semantics. If the **residual's** inputs are missing, retain/widen the needed projection and rebind before narrowing the output, or reject the shape. Don't change the session setting or use a bare `ParquetSource::with_predicate` as an exact-filter promise. Native SQL can safely honor row-pushdown-on sessions by using residuals instead; plan display should distinguish that from actual row pushdown.

Use [#132]'s planner contract: `off` uses stock; `prefer` delegates the **whole query** only for a classified unsupported shape; `required` returns a planning error with the offending feature and scan/table (for example, `native Parquet morsels do not support OFFSET on t`). Report real planning and execution errors in both opt-in modes, not as `Unsupported`. Never switch paths after starting a native scan. `EXPLAIN` should identify the actual native Parquet source, operators and count sink, not just the presence of `MorselExec`; follow #132 for nested views and `EXPLAIN ANALYZE` so strict mode cannot run stock implicitly.

## Test plan for #126

- **Reproduce the handoff gap.** Drive the real stock `ParquetSource::create_morselizer` to its first `MorselPlan` with a morsel, allowing footer reads but gating data range reads in a test reader. The stock morsel's first poll can start a range request and return `Pending` without yielding a batch. With the experimental constructor, require that the same gate blocks a pending planner instead: no ready reader is published before the requested data arrives, and draining a published reader never starts new I/O. This is a contract test for the new path, not a change to the stock stream behavior.
- **SQL and Arrow parity.** In dedicated Parquet coverage alongside [`core/tests/morsel_execution.rs`][fork-tests], use the same deterministic files in `off` and `required`: at least two files with multiple small row groups, disjoint row IDs and nullable predicate values. Put both matches and nonmatches in surviving groups, and at least one group outside the filter range. Compare unordered row **multisets** and exact output schema for `SELECT payload AS p, id FROM t WHERE gate > 10`, including sessions with row pushdown off and on. Keep `gate` out of the final projection; assert a pruning counter and retain a mixed group to catch incorrect removal of the residual. Exercise a schema requiring per-file adaptation if admitted. Use SQL for the contract and public DataFrame/plan APIs for schema and path assertions.
- **Real count path.** Run `SELECT COUNT(*) AS n FROM t WHERE gate > 10` on the same fixture, with no metadata proof of the answer. Compare one row and the known count to stock, including a non-nullable `Int64` field named `n`. Assert native Parquet source and count sink in the plan, **and** execution evidence: successful data range fetches or decoder reader creation, multiple exclusive reader claims, rows passed to the counters after filtering, and one count finalize before publishing the result. Footer reads, a plan label alone or a matching scalar cannot establish this. Include a zero-width projection case separately so counting does not depend on a materialized payload.
- **Exactly once and no premature EOF.** With a controlled reader/store, gate data (not merely footer) I/O after some readers have drained, so the ready queue is empty while another lane is pending. Verify neither stream EOF nor count finalization, then release the gate and verify all expected rows and one finalize. Record stable test IDs by file occurrence and row-group index (or reader ordinal with a checked decoder frontier); assert publication/claim/drain once per emitted reader, no claims for pruned groups, and multiple workers claiming from one stock file group. Use barriers rather than opportunistic scheduling to establish simultaneous claims. Repeat with empty input, all row groups pruned after metadata, and all rows rejected after decode; none may hang or lose the zero count. Repeat/concurrently execute the same plan to check isolation.
- **Bounds, error and cancellation.** Use instrumented planner futures and a gated object store. With small caps (including capacity one), stall the sink/reader and assert high-water marks for active lanes, data/metadata futures, reserved/queued readers and worker-owned readers. Resume to prove progress. Drop the result with I/O pending and with a full queue/sink; assert owned futures, readers and permits are released and no more work is admitted. Inject a pending-phase I/O error and a decode error while peers are blocked; verify the error reaches the consumer, teardown does not require it to drain results first, and no partial count is finalized. Add timeouts to every gated scenario.
- **Rejection and stock regression.** Test `prefer` versus `required` on representative unsupported ordering and offset queries and a configured unsupported file layout; assert stock output/path in `prefer` and a reason-bearing planning failure in `required`. Keep `FileStream` regressions such as `morsel_pending_planner_does_not_block_active_reader` and file sharing/order tests passing. Run `cargo test -p datafusion --test morsel_execution` (plus the dedicated target if separate), `cargo test -p datafusion-datasource-parquet`, `cargo test -p datafusion-datasource file_stream`, and relevant lint checks with explicit timeouts on the pinned toolchain.

## Open choices after the first slice

Tune lane, I/O and ready capacities independently; measure whether CPU reader preparation bottlenecks a single producer before moving it to more CPU tasks. Decide whether to add byte reservations or subdivide large row groups; coordinate with the memory pool and measure buffering in the store as well as in the ready queue. Revisit exact row-filter pushdown, finer-grained split ownership and ordered/distributed outputs only with their own semantics and tests. These choices do not require rearranging the stock scan runtime in #126.
