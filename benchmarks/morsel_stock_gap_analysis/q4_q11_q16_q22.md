# Morsel vs. Stock Gap Diagnosis: TPC-H SF5 Q4, Q11, Q16, and Q22 (#216)

## Executive Summary

In the Wave-4 22/22 TPC-H SF5 scorecard (`#209`,
[sf5_22q_wave4_scorecard.md](../morsel_tpch/sf5_22q_wave4_scorecard.md)),
single-config `morsel_pushdown` (`morsel_mode=required`) beats both
`stock_default` (`0.83×` geomean) and `stock_pushdown` (`0.90×`), but still
trails `stock_default` on four small-to-medium queries (`125–230 ms` total wall
time):

| Query           | `stock_default` | `stock_pushdown` | `morsel_no_pd` | `morsel_pushdown` | `duckdb_default` | Gap vs. `stock_default` | Primary Root Cause(s)                                                                                                                                                                                            |
| --------------- | --------------: | ---------------: | -------------: | ----------------: | ---------------: | ----------------------: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`q16`**       |    **132.6 ms** |         143.4 ms |       169.5 ms |          172.0 ms |         141.0 ms |    **+39.4 ms (1.30×)** | `stage_0` cap-4 channel throttling (`~19–24 ms`) + forced `RowFilter` on 8-RG `part` (`~5–8 ms` build) + net `~13.6 ms` residual (`part` `join_finalize` & `main` tail, partly offset by faster probe/`stage_0`) |
| **`q4`**        |    **201.1 ms** |         291.4 ms |       311.3 ms |          226.5 ms |         191.7 ms |    **+25.4 ms (1.13×)** | `JoinBloomFilterExpr` (`24.7%` cycles / `~350 ms` CPU on 30M rows) + unspecialized `BuildSemi` loop (`4.9%` in `pd`, `65.0%` in `no_pd`) + `keep_dynamic_preds_in_bulk=false`                                    |
| **`q11`**       |    **112.9 ms** |         127.9 ms |       190.3 ms |          135.2 ms |          95.7 ms |    **+22.3 ms (1.20×)** | 26–34/64 `partsupp` RGs run in slow `RowFilter` during adaptive probe + Bloom dropped in `BulkDecode` + `SingleHashTable` vs. Stock `ArrayMap` + `~2.0 ms` extra 1-RG build overhead                             |
| **`q22`**       |    **124.0 ms** |         142.3 ms |       169.0 ms |          126.3 ms |         144.7 ms |     **+2.3 ms (1.02×)** | Same unspecialized `BuildAnti` (`17.2%` cycles) + scalar Bloom (`12.8%` cycles) + 6-RG `customer` core starvation (`119.1 ms` `ready_wait`)                                                                      |
| **4-Query Sum** |    **570.6 ms** |         705.0 ms |       840.1 ms |      **660.0 ms** |         573.1 ms |    **+89.4 ms (1.16×)** | **Closable to ~542–577 ms with Ranks 1–5 (includes unmeasured `q4` fused-Bloom and `q11` Rank 5 estimates; `~585 ms` from ablation-proven toggles alone)**                                                       |

Every finding below is backed by: (1) quiet-host SF=5 Wave-4 baseline runs on
`rob-tandy-dduck2` (`78e46e910`, `92–93%` host idle, 100% warm `mincore` page
residency, 8 pinned ARM Neoverse-N1 cores), (2) quiet-host side-by-side physical
plans and Stock `EXPLAIN ANALYZE` (`profile_4q.py plans`, `93%` host idle), (3)
quiet-host Arm PMUv3 hardware counters (`perf stat`: `cycles:u`,
`instructions:u`, IPC, `r17:u` L2d cache refills), (4) quiet-host `perf record`
leaf CPU profiles (`3,999 Hz cycles:u`, `0` lost samples, 21K–59K samples per
profile), and (5) quiet-host reproducible scratch phase-timeline probes and
counterbalanced ablations (`q4_q11_q16_q22/ablations.patch` +
`profile_4q.py ablations`, `92–99%` idle, 100% Arrow table parity verified,
including same-session `stock_default` arms on `q16` and `q11`).

**Key headline from quiet-host scratch ablations
(`q4_q11_q16_q22/ablations.patch`):**

- **On `q16`:** In 7-round same-session quiet ablations (`baseline_pushdown =
166.3 ms` vs. same-session `stock_default = 125.8 ms`, gap `+40.5 ms`),
  widening `ensure_stage`'s output channel from `4 → 16` (`result_capacity(8)`,
  within `MAX_RESULT_CAPACITY = 32`) or `32` / `64` (`dag.rs:660`) **alone**
  cuts quiet `q16` exec by **`−20.0 / −17.9 / −19.2 ms`** (`stage_0` `agg_emit`
  `42.0 → 15.5 ms`). Avoiding forced `RowFilter` on 8-RG `part` (`small_bulk`)
  cuts `build_0` (`28.2 → 18.8 ms`) and net exec by **`−5.2 ms`** (`−38.7 ms`
  CPU); `stage_cap16+small_bulk` reaches **`139.4 ms` (`−26.9 ms`)**, leaving a
  **`+13.6 ms` same-session residual** vs. `stock_default` (`125.8 ms`; `+4.9 to
+9.6 ms` on `dduck1`). Adding concurrent independent builds (`part` +
  `supplier`, a gain _beyond_ Stock since Stock also serializes `supplier`) plus
  NEON + prefetch Bloom reaches **`126.7 ms` exec (`−39.6 ms`, `par: 4.62× →
5.74×`)**, within `+0.9 ms` of same-session `stock_default` and projecting
  **`~128–139 ms`** total with Ranks 1–5 (beating DuckDB `141.0 ms`).
- **On `q22`:** Adding a batch-inlined flat-int `BuildSemi`/`BuildAnti` probe
  loop (`probe_mark_radix_flat_int`) cuts quiet `q22` probe process time
  **`2.29×` (`112.0 → 49.0 ms`)**, exec CPU by **`−62.8 to −69.2 ms`**, and
  exec wall by **`−8.2 to −8.7 ms`**; adding NEON + prefetch Bloom yields
  **`−67.0 to −70.0 ms` CPU** (`−8.3 to −9.9 ms` wall), projecting `q22` to
  **`~116–120 ms`** (`−4 to −8 ms` faster than `stock_default`, `−25 to
−29 ms` faster than DuckDB).
- **On `q4`:** The `+110 ms` `morsel_no_pushdown` deficit is `65.0%`
  unspecialized `BuildSemi` probing across 64 radix partition tables (`8.0 MiB`
  random scatter, IPC `1.51`, `22.56M` L2d refills); `probe_mark_radix_flat_int`
  alone cuts `no_pushdown` by **`−480.8 ms` CPU (`−59.9 ms` wall)**, and
  `bloom_fast + fast_semi` / `force_bulk + keep_dyn + bloom_fast + fast_semi`
  cut quiet `morsel_pushdown` by **`−12.1 to −15.4 ms` wall** (`−28 to
−70 ms` CPU). Closing the remaining `~10–13 ms` gap is analytically estimated
  (unmeasured) to require fusing a compact L2-resident 1-word (64-bit)
  register-blocked Bloom prefilter directly into `probe_mark_radix_flat_int`
  (operating on the `18.97M` post-`l_receiptdate > l_commitdate` rows after
  `407.5 ms` bulk decode instead of `~350 ms` `RowFilter` Bloom on all `30M`
  rows), projecting **`~184–198 ms`** (`−28 to −42 ms` vs. current `226.5 ms`).
- **On `q11`:** Per-RG `[DIAG_ADAPT]` timings on `partsupp` are near-parity
  (`1.00×–1.35×` across quiet runs, with `main` occasionally committing to
  `RowFilter`), so wave-1/2 probing leaves `26–34 / 64` RGs in `RowFilter`, and
  `keep_dynamic_preds_in_bulk = false` drops the 4 KiB L1-resident Bloom filter
  once switched. In 7-round same-session quiet ablations (`baseline_pushdown =
123.1 ms` vs. `stock_default = 104.9 ms`), **`force_bulk+keep_dyn`** (without
  `bloom_fast`) cuts exec by **`−12.1 ms` (`110.9 ms`, `−72.0 ms` CPU)** —
  within `+6.0 ms` of same-session `stock_default` — whereas `force_rf`
  regresses `+10.5 ms` and `bloom_fast_neon` alone adds `+4.4 ms` (`Rank 2` on
  `q11 = 0 ms`). Adding a dense `ArrayMap`/bitset join path plus a 1-RG fast
  path (Rank 5) is an unmeasured estimate of **`−5 to −8 ms`** (`135.2 →
~114–120 ms`). Optional Stage CSE (eliminating the already-trimmed `49.2 ms`
  `scalar_sq_0` stage, an incremental `−40 to −46 ms` on top of Ranks 1–5)
  projects **`~68–80 ms`**, beating DuckDB (`95.7 ms`).

#### Physical Plan, Join Direction, and `o_orderdate` Pruning

- **Identical join direction and zero RG pruning:** Both Stock and Morsel place

[193..29,999,589]`, overlapping all `240 / 240` `lineitem` RGs. All four arms

- **Why `stock_default` (`201.1 ms`) beats `stock_pushdown` (`291.4 ms`) by

#### Why `morsel_no_pushdown` Is `+110.2 ms` Slower (`311.3 ms`, `2,215 ms` CPU)

Morsel's bulk Parquet scans (`orders 265.5 ms + lineitem 407.5 ms = 673.0 ms`
CPU) match `stock_default`'s quiet `DataSourceExec` (`255.5 + 397.5 = 653.0 ms`
CPU). The entire `+110 ms` deficit (`+937 ms` CPU!) comes from ONE path:
`HashJoinProbe::next_chunk_radix` (`hash_join.rs:4519–4544`) for
`BuildSemi`/`BuildAnti`:

1. **No specialized batch loop (`65.0%` of all cycles!):** Unlike
   `Inner`/`BuildOuter` (which use `probe_collect_radix_flat_int`), `BuildSemi`
   loops row-by-row calling `probe_row_at` (`5.93%`) → `ProbeKeys::hash_at`
   (`2.40%`, 1st `mix_u64` + enum dispatch) → `probe_mark_all_matches`
   (`45.91%`, 2nd enum dispatch + **2nd `mix_u64`**!) + `next_chunk_radix`
   overhead (`10.73%`).
2. **L2 cache thrashing across 64 radix tables (`8.0 MiB` random scatter):**
   Because `287,250 > RADIX_JOIN_THRESHOLD_ROWS (16,384)`, `orders` is split
   into 64 separate `FlatIntTable`s (`8,192` 16-byte slots × 64 = **`8.0 MiB`**,
   `8×` larger than the 1 MiB per-core L2!). Every worker scatters 18.97M probes
   randomly across all 64 tables, lowering IPC to **`1.51`** (`22.56M` L2d
   refills, `+77.3%` cycles vs. `stock_default`).
3. **Quiet ablation proof:** Adding `probe_mark_radix_flat_int` (`no_pushdown +
fast_semi`) alone cuts `morsel_no_pushdown` by **`−480.8 ms` CPU (`2,206.9 →
1,726.0 ms`)** and **`−59.9 ms` wall (`297.4 → 237.5 ms`)**, leaving the
   remaining `~448 ms` CPU gap vs. `stock_default` due strictly to the `8.0 MiB`
   L2 miss footprint.

  `supplier` rows, `32 KiB` for 1 `nation` row) and probes all `8.0M` `partsupp`
  rows across both scans via direct `O(1)` integer indexing with **zero
  hashing** (`ArrayMap::get_matched_indices = 8.54%` CPU, **`2.08` IPC**!).
  Quiet `EXPLAIN ANALYZE` for `stock_default` shows `partsupp DataSourceExec =
448.5 ms` (`234.7 + 213.9 ms`) and `HashJoinExec = 109.8 ms` (`42.9 + 13.0 +
41.8 + 12.0 ms`; `exec = 99.9 ms`, `exec CPU = 662.4 ms`).

  `stock_default` by **`+26.2 ms` exec (`126.1` vs. `99.9 ms`; `−3.8 ms` plan
  gives `+22.3 ms` total)** despite retiring **3.5% fewer instructions**
  (`3,037M` vs. `3,146M`) and **12.9% fewer L2d refills** (`8.39M` vs. `9.63M`)!

#### Exact Attribution of `q11`'s `+26.2 ms` Exec Deficit

1. **Adaptive probe tax on 32-RG `partsupp` scans (`−12.1 ms` wall / `−72.0 ms`
   CPU in 7-round same-session quiet ablation):**
   - Per-RG `[DIAG_ADAPT]` timings on `partsupp` are **near-parity** across
     quiet runs (`scalar_sq_0`: `128.9` vs. `95.4 ns/row` [`1.35×`]; `main`:
     `104.5` vs. `101.5 ns/row` [`1.03×`], and `main` occasionally commits to
     `RowFilter` at near-`1.0×`). Because per-RG probe noise is close to the
     mode margin, we rely on the **end-to-end quiet ablations** below to
     establish that `BulkDecode` wins decisively.
   - Why does `RowFilter` lose end-to-end even at `4%` selectivity?
     `ps_supplycost` is a `FIXED_LEN_BYTE_ARRAY` (`Decimal128`, `451.5 KiB`
     compressed / `757.5 KiB` uncompressed per RG, `PLAIN + RLE_DICTIONARY`). At
     `4%` uniform random selectivity (`160K / 4M`), `RowSelection` produces
     ~154K `Select(1) / Skip(24)` segments that **cannot skip any Zstd pages**
     while adding `JoinBloomFilterExpr` (`4.88%` CPU = `~38.5 ms`) and
     `RowSelection` overhead!
   - Because each `partsupp` scan has only **32 RGs across 8 workers (`4`
     RGs/worker)**, wave-1 (`2 RF + 2 Bulk + 4 default RF`) and wave-2 dispatch
     run **`26–34 / 64` `partsupp` RGs (`41–53%` of the entire table!) in
     `RowFilter`** (`RF/Bulk = 30/38` to `38/30`, including 4 build RGs) before
     committing to `BulkDecode`.
   - Once committed to `BulkDecode`, `keep_dynamic_preds_in_bulk = false`
     (`morsel.rs:4806`) drops the tiny `4 KiB` L1-resident Bloom filter, sending
     all remaining rows into `probe_collect_matches` (`13.04%` CPU = `~103 ms`).
   - **Same-session quiet ablation proof (7 counterbalanced rounds):**
     `baseline_pushdown` = `123.1 ms` exec (`795.5 ms` CPU) vs. same-session
     `stock_default` = `104.9 ms` (`679.1 ms` CPU). **`force_bulk+keep_dyn`**
     (without `bloom_fast`) cuts `q11` by **`−72.0 ms` CPU (`795.5 → 723.6 ms`)**
     and **`−12.1 ms` exec wall (`123.1 → 110.9 ms`)** (`force_bulk` alone saves
     `−4.6 ms`, `force_rf` regresses `+10.5 ms` / `+28.0 ms` CPU, and
     `bloom_fast_neon` alone adds `+4.4 ms` / `+16.2 ms` CPU while
     `force_bulk+keep_dyn+bloom_fast` = `113.2 ms` — confirming NEON Bloom gives
     no wall gain on `q11`, so Rank 2 on `q11` is `0 ms`!).
2. **Extra worker-barrier overhead on 4 sequential 1-RG builds (`~2.0 ms` extra
   wall over Stock / `27.4 ms` `ready_wait`):** Stock nests
   `CollectLeft(nation)` over `CollectLeft(supplier)`, so Stock **also** builds
   those four 1-RG tables serially (`~5.4 ms` total in quiet `EXPLAIN ANALYZE`:
   `0.65` and `2.66 ms` in the scalar subquery, `0.28` and `1.85 ms` in `main`).
   Morsel takes `7.4 ms` (`1.1`, `3.3`, `0.9`, and `2.1 ms`) — **`~2.0 ms` extra
   wall over Stock** — because each 1-RG build spawns 8 Tokio workers, wakes 1
   worker, and parks 7 workers (`ready_wait = 6.4 + 8.5 + 5.8 + 6.7 = 27.4 ms`).
   Moreover, both engines build `nation` (`1` row) and `supplier` identically
   twice.
3. **`SingleHashTable` hashing vs. Stock's `ArrayMap` (`~4–6 ms` wall):**
   `probe_collect_matches` (`13.04%` CPU, `~103 ms`) hashes `ps_suppkey` against
   the 2,003-row `SingleHashTable` (contributing to `1.85` vs. Stock's `2.08`
   IPC), whereas a direct `50,000`-entry bitset (`6.25 KiB`, 100% L1d-resident)
   or dense `ArrayMap` probes `ps_suppkey` in 2 instructions with zero hashing
   (and also eliminates the `2.24×` L2d refill / `1.33` IPC penalty in
   `morsel_no_pushdown`).
4. **Bonus (beyond Stock parity — beats DuckDB `95.7 ms`):** Notice
   `scalar_sq_0` computes `SUM(value) * 0.00002` over the exact same
   `partsupp ⋈ supplier ⋈ nation` relation as `main`'s `GROUP BY ps_partkey`.
   Stage CSE / subquery reuse eliminates the entire `scalar_sq_0` stage
   (`55.7–63.1 ms` baseline, trimmed to `49.2 ms` under `force_bulk+keep_dyn`,
   giving an incremental **`−40 to −46 ms`** on top of Ranks 1–5 →
   **`~68–80 ms`** total!).

### Concrete Implementation Notes for Follow-Up PRs

1. **Rank 1 (`dag.rs:660`):** Batches waiting inside `ensure_stage`'s
   `mpsc::channel` are not charged to `MemoryPool` until the receiver calls
   `MaterializedStage::try_push`. Simply raising `sink_capacity.max(4)` to `64`
   would allow up to `16×` more uncharged batches in flight and exceed
   `MAX_RESULT_CAPACITY = 32` (`morsel.rs:118–121`, where `result_capacity`
   caps at `MAX_RESULT_CAPACITY`), risking OOM under tight memory limits. Quiet
   `profile_4q.py ablations` sweeps (`stage_cap16 / 32 / 64`: `146.3 / 148.4 /
147.1 ms` vs. `166.3 ms` baseline) confirm that **`result_capacity(workers)`
   (`= 16` at 8 workers, already capped at `MAX_RESULT_CAPACITY = 32`) captures
   the full `−20.0 ms` win**. To capture this gain safely across all multi-stage
   radix aggregates (`q13`, `q16`, `q18`), either (a) raise `ensure_stage`'s
   channel capacity to `result_capacity(stage_pipeline.workers)`
   (`≤ MAX_RESULT_CAPACITY = 32`) or (b) charge
   `SharedStageMemory::try_add_batch` **before** enqueueing (or collect
   per-partition batches directly into a pool-charged `Mutex<MaterializedStage>`,
   removing the intermediate channel altogether).
2. **Rank 2 (`hash_join.rs` + `join_filter.rs`):**
   - Port the `probe_collect_radix_flat_int` batch-inlined macro pattern to
     `BuildSemi`/`BuildAnti` (`probe_mark_radix_flat_int`): single `mix_u64`,
     zero per-row enum dispatch.
   - Align `SplitBlockBloomFilter` blocks (`#[repr(C, align(32))]`), add a
     fast 1-word (64-bit, 2-bit-per-key or 4-hash) register-blocked prefilter
     option (`64–256 KiB`, strictly L2-resident!) directly on
     `FinalizedHashTable`, and evaluate it inside `probe_mark_radix_flat_int` /
     `probe_collect_radix_flat_int` so `BulkDecode` pipelines reject `95%+` of
     non-matching probe keys in L2 cache without touching the `4–8 MiB`
     64-partition radix tables **or** allocating `BooleanArray`/`RowSelection`.
3. **Rank 3 (`morsel.rs:2454`):** Group `run_build_pipelines` into dependency
   waves based on `dynamic_join_filters` edges; within any wave of independent
   builds (like `q16`'s `part` and `supplier`), launch them concurrently under a
   shared `JoinSet` so a 1-RG build never stalls 7 idle cores. Note that the
   scratch `MORSEL_DIAG_CONCURRENT_BUILDS=1` ablation is a minimal two-Parquet
   probe that skips `short_circuits_on_table`/`ShortCircuitAll` (empty build,
   null-aware anti with a NULL key) and instantiates an empty `DagRuntime`; the
   production implementation (~80 LOC, medium risk, matching `#215`) must preserve
   short-circuit cancellation, `DagRuntime` stage dependency tracking, and
   wave-barrier `published_filters` propagation.
4. **Rank 4 (`buffered.rs` + `morsel.rs:4806`):**
   - Refine `can_skip_columns` and the `estimated_scan_rgs < 12` heuristic: when
     a scan has no dynamic join filter and projected payload columns represent
     `< 25%` of total decoded column width (like `q16` `part` where `p_partkey`
     is 1 of 4 columns, or `q22` `customer` where `c_phone` + `c_acctbal` are
     both in the predicate), default to `BulkDecode` instead of `RowFilter`.
   - For medium scans (`12 <= estimated_scan_rgs <= 48`, like `q11` `partsupp`
     32 RGs), reduce wave-1 default dispatch while probing (`probe_rgs_per_mode
= 1` and alternate `RF`/`Bulk` during wave 1 instead of defaulting all
     remaining wave-1 RGs to `RowFilter`), and pass `keep_dynamic_preds_in_bulk
= true` when the build table is selective (or rely on Rank 2's in-join
     register-blocked Bloom).
5. **Rank 5 (`hash_join.rs`):** Add a dense `ArrayMap` / bitset representation
   for `SingleHashTable` when single-column integer build keys have small span
   (`max - min <= 262_144` and density `>= 1%`, covering `q11` `supplier` both
   filtered `[1..50,000]` and unfiltered), matching Stock's `2.08` IPC lookup.
