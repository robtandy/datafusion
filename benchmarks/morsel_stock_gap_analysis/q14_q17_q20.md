# Morsel vs. Stock Pushdown Gap Analysis: TPC-H SF5 Q14, Q17, and Q20 (#215)

This diagnostic report isolates every millisecond of the remaining SF=5
warm-cache wall-time gap between single-config **Morsel (`morsel_pushdown`,
`morsel_mode=required`)** and **Stock DataFusion (`stock_pushdown`,
`morsel_mode=off`)** on **TPC-H Q14, Q17, and Q20** after Wave-4 (`#209`). Every
root cause is verified with side-by-side `EXPLAIN` / `EXPLAIN ANALYZE VERBOSE`
metrics, Arm PMUv3 hardware counters (`perf stat`), 3,999 Hz leaf CPU profiles
(`perf record`), and **counterbalanced quiet-host disposable scratch ablations**
(100% warm Linux page cache via `mincore`, 100% lossless Arrow IPC parity).

## Executive Summary

In Wave-4 (`benchmarks/morsel_tpch/sf5_22q_wave4_scorecard.md`),
`morsel_pushdown` trailed `stock_pushdown` by **`+40.5 ms` on `q14`** (`341.1`
vs. `300.6 ms`), **`+31.8 ms` on `q17`** (`499.8` vs. `468.0 ms`), and
**`+6.7 ms` on `q20`** (`329.3` vs. `322.6 ms`) — **`+79.0 ms`** combined.

Clean quiet-host measurements (`rob-tandy-dduck2`, 8 pinned Neoverse-N1 cores
`taskset -c 0-7`, `93–99%` host idle pre/post) reproduce those exact baselines
and show that **six concrete fixes not only close all three gaps vs.
`stock_pushdown`, but also place `morsel_pushdown` below BOTH `stock_pushdown`
and the Wave-4 DuckDB 2.0.1 reference medians (measured in a separate session on
the same host and SF=5 dataset) on all three queries**:

### Root Causes at a Glance

1. **Q17 (+39.2 ms repro / +31.8 ms Wave-4): `is_infallible_expr` bug triggers
   `eval_staged` copy + scalar bit-scatter over 60M rows.**
   `datafusion/datasource-parquet/src/row_filter.rs::is_infallible_expr` does
   not recognize `JoinBloomFilterExpr`, so `l_partkey >= 2409 AND l_partkey <=
998971` (99.66% pass rate!) and `morsel_bloom_filter(l_partkey)` run via
   `DatafusionArrowPredicate::eval_staged`. On almost every 8,192-row batch
   across 60M rows, `eval_staged` allocates and copies 99.66% of `l_partkey` via
   `filter_record_batch` and scatters the result bit-by-bit in a scalar loop
   (`BooleanArray::value` `9.67%` plus `DatafusionArrowPredicate::evaluate`
   `5.08%` plus extra `__memcpy_generic` `1.65%` = **`16.4%` / `1.33G` wasted
   user cycles**). Morsel's L1-resident split-block Bloom filter is **already
   faster than Stock's `HashTableLookupExpr` (`Lookup::Routed`)** — fixing
   `is_infallible_expr` alone cuts Q17 by **`−84.6 ms` (`500.5 → 415.9 ms`)**,
   dropping `row_pushdown_eval_time` from `1,130 ms → 572.0 ms` (and to
   `489.2 ms` with redundant range elision, or `528.8 ms` in
   `morsel_combined_best` across all 488 `RowFilter` RGs, vs. Stock's
   `839.3 ms`).
2. **Q14 (+45.3 ms repro / +40.5 ms Wave-4): Wrong build side (`part` 1M rows
   vs. filtered `lineitem` 374.2K rows) + cross-core atomic Bloom build
   contention (`__aarch64_ldset4_relax`).**
   Stock DataFusion beats **both** Morsel (`341.1 ms`) **and** Wave-4 DuckDB
   2.0.1 (`336.5 ms`) on Q14 because Stock is the only engine that applies
   Parquet min/max interval selectivity (`l_shipdate` 1-month window ≈ `1.19%` →
   `~357K` rows < `part`'s `1.0M` rows) to build on **filtered `lineitem`** (no
   string columns, 2.67× smaller hash table, 68.8% of `part` pruned before
   decoding `p_type`, zero dynamic filter on 30M `lineitem` rows). Both Morsel
   (`pipeline_filter_shift` assumes 50% selectivity for a single-column range)
   and DuckDB build on unfiltered `part` (1M rows). Worse, Morsel then builds a
   useless 2 MiB `AtomicSplitBlockBloomFilter` across 8 cores with LSB-indexed
   atomic `fetch_or` (`__aarch64_ldset4_relax`: **`4.73%` of all Q14 cycles**,
   `+8.65M` L2D refills, `join_finalize = 36.6–37.9 ms` wall) and pushes it onto
   30M `lineitem` rows where it prunes **0 rows**
   (`predicate_cache_inner_records = 29.61M`, `row_pushdown_eval_time = 71.4 ms`
   vs. Stock `28.0 ms`). Switching to Parquet-statistics interval selectivity
   (`+stats_build`), addressing the wave-1 `AdaptiveRowFilter` `BulkDecode`
   trade-off (`buffered.rs:604`, scoped carefully to avoid `q6`/`q15`
   regressions — see §3.4), and aligning radix Bloom blocks to the exact
   level-0 radix bits `[51..57)` drops Q14 to **`276.2 ms`** (with `ra2x`).
3. **Q20 (+1.6 ms repro / +6.7 ms Wave-4): Missing transitive equijoin
   `s_suppkey` dynamic filter on `lineitem` (`stage_0`) + sequential single-RG
   `supplier` build.**
   In `datafusion/core/src/morsel/parquet.rs::remap_probe_key_to_scan`,
   tracing `supplier`'s `s_suppkey` dynamic filter (`2,028` keys, `4%`
   selectivity) backward through `partsupp`'s `BuildSemi` join bails at
   `mid_probe.needs_build_emission()` and `JoinOutputCol::Build(_)`, even though
   `ps_suppkey == l_suppkey` is an exact equijoin key. Consequently, `lineitem`
   only receives `partsupp`'s composite `(l_partkey, l_suppkey)` Bloom filter
   plus loose `[min, max]` bounds, forcing `l_partkey` (`153.6 MB` compressed)
   to be decoded and hashed for **4.28M rows instead of 170K rows** and
   inflating `predicate_cache_records` **19.1×** (`46.07M` vs. Stock `2.41M`).
   Enabling equijoin substitution drops `predicate_cache_records` `46.07M →
2.49M` and saves **`−16.2 ms`** immediately (`324.4 → 308.2 ms`).
   Additionally, Morsel runs `nation -> supplier` (`14.4 ms` on 1 RG, 7 cores
   idle) **serially** before `part` (`19.7 ms`), whereas Stock runs them
   concurrently (`24.6 ms` combined vs. Morsel's `34.1 ms`).
4. **All three queries (`−16` to `−21 ms` each, `−54.1 ms` combined): Two-phase
   `RowFilter` ready-queue slot starvation (`ready_wait`).**
   `datafusion/core/src/morsel/parquet.rs:565` sizes the shared `ready::channel`
   slot semaphore to `read_ahead = workers = 8`. Under two-phase `RowFilter`
   I/O, a row group holds one of those 8 permits across Phase-1 I/O, ready
   queueing, worker `RowFilter` evaluation, Phase-2 I/O (`spawn_blocking`
   `get_ranges`), and post-Phase-2 queueing — structurally starving 8 workers
   (`peak_ready_depth = 4–6` < 8 workers, `ready_wait = 106–198 ms`). Doubling
   `chan_cap` to `read_ahead * 2 = 16` for pushed-filter scans cuts `ready_wait`
   on the `ra2x` step alone by **29–63%** (`91.0 → 33.9 ms` / `−62.7%` on Q14,
   `103.5 → 73.3 ms` / `−29.2%` on Q17, and `197.8 → 83.0 ms` / `−58.0%` on Q20;
   `124.6 → 29.1 ms` / `−76.6%` in the re-verified `[51..57)` Q14 sweep) and
   saves **`−20.4` to `−21.1 ms` (Q14), `−17.0 ms` (Q17), and `−16.0 ms` (Q20)**
   in pure wall time.

### 2.3 Accounting for `#138` `Agg fin / other` (`74.1 / 86.7 / 89.1 ms` in Wave-4)

In the Wave-4 scorecard, `Agg fin / other` is defined as the wall-time residual
`exec_ms − (decode_ms + process_ms) / 8 − join_fin_ms − sort_fin_ms`. Actual
`AggregateSink::finalize` on Q14 (`1` ungrouped row), Q17 (`1,021` + `1` rows),
and Q20 (`1,210` rows) takes `< 1 ms`. Using the exact 8-core capacity identity
`8 × exec_ms = exec_cpu_ms + idle_core_ms`, the residual decomposes **without
double-counting `join_fin_ms`** into three exact terms that sum to the
observed quiet-host baseline residual:

- **Term A — Net non-worker CPU/core (`(exec_cpu_ms − decode_ms − process_ms) /
8 − join_fin_ms − sort_fin_ms`):** CPU burned outside worker `decode`/`process`
  clocks beyond the already-subtracted `join_fin_ms` wall time — primarily
  `spawn_blocking` `LocalFileSystem::get_ranges` page-cache copies
  (`pending_io_ms = 320.3 / 596.1 / 331.4 ms`), `join_combine`,
  `AggregateSink::finalize`, and Tokio runtime overhead.
- **Term B — Measured `ready_wait / 8`:** worker idle time blocked inside
  `ReadyReaders::claim()` due to two-phase `RowFilter` semaphore starvation
  (`slots = 8` for 8 workers).
- **Term C — Unmeasured idle / barrier / tail-skew remainder (`(8 × exec_ms −
exec_cpu_ms − ready_wait_ms) / 8`):** idle core time outside `ready_wait`,
  including end-of-pipeline worker tail skew (e.g., Q14 `probe` claims `22..41`
  across 8 workers; Q17 `build` `23..36`; Q20 `stage_0` `24..34`), serial
  single-RG pipelines (Q20 `supplier` 1 RG = `14.4 ms` while 7 workers exit),
  and inter-pipeline barrier/task teardown.

| Query     | Quiet `exec` ms | `(dec+proc)/8` + `jfin` + `sfin` | Residual (`Agg fin / other`) | Term A: Net non-worker CPU/8 | Term B: `ready_wait/8` | Term C: Unmeasured idle / tail skew | Sum (A + B + C) |
| --------- | --------------: | -------------------------------: | ---------------------------: | ---------------------------: | ---------------------: | ----------------------------------: | --------------: |
| **`q14`** |         `330.4` |      `195.0 + 22.6 + 37.9 + 0.0` |                   **`75.0`** |                       `24.2` |                 `13.2` |                              `37.6` |      **`75.0`** |
| **`q17`** |         `485.5` |        `388.5 + 3.2 + 0.8 + 0.0` |                   **`93.1`** |                       `38.1` |                 `20.0` |                              `35.0` |      **`93.1`** |

### 3.3 Why `AtomicSplitBlockBloomFilter` Burned 4.73% of All Q14 Cycles

In `datafusion/core/src/morsel/hash_join.rs::finalize_radix_all_in_memory`, 8
workers process 64 level-0 radix partitions defined in
`datafusion/core/src/morsel/radix.rs` (`RADIX_MAX_HIGH_BIT = 57`,
`DEFAULT_RADIX_BITS = 6`, `level0_shift(6) = 51`), so partition `p = (h >> 51)
& 63` uses middle hash bits **`[51..57)`** (disjoint from `hashbrown`'s top-7
`h2` tag bits `[57..64)`). Yet `AtomicSplitBlockBloomFilter::insert`
(`join_filter.rs:197`) indexes blocks by the **low bits** (`(h as usize) &
block_mask`) using atomic `word.fetch_or(bit, Ordering::Relaxed)`. Every worker
therefore collides on random cache lines across the entire 2 MiB Bloom array,
triggering 8M atomic `LDSET` instructions, `+8.65M` extra L2D refills, and
collapsing IPC from `2.41 → 2.05`.

Aligning `SplitBlockBloomFilter` directly to the radix partition bits `[51..57)`
solves this cleanly for all power-of-two `num_blocks >= 64` (keeping `fetch_or`
for `< 64` blocks):

- **Block index:** `idx = ((((h >> 51) & 63) as usize) << sub_bits) | ((h as
usize) & sub_mask)`, where `sub_bits = num_blocks.trailing_zeros() - 6 <= 12`
  (since `MAX_BLOOM_BYTES = 8 MiB` → `2^18` blocks).
- **Intra-block hash word:** `x = (h >> 19) as u32` (bits `[19..51)`, disjoint
  from both `[51..57)` and `[0..12)`).

Each of the 64 radix finalize partitions then owns a **strictly disjoint,
contiguous slice `[p << sub_bits .. (p + 1) << sub_bits)`**, allowing plain
relaxed load/store with zero atomic RMWs and zero cross-core cache-line
bouncing. With this `[51..57)` layout, `MORSEL_SCRATCH_NONATOMIC_BLOOM=1`
verified **100% exact 8-worker SF=5 Arrow IPC parity against `stock_pushdown`**
across `q7` (3/3), `q8` (3/3), `q9` (10/10), `q10` (3/3), `q14` (3/3), `q17`
(3/3), `q18` (3/3), `q20` (3/3), and `q21` (3/3).

Because `run_build_pipelines` (`datafusion/core/src/morsel.rs:2452`) awaits
each build pipeline sequentially (`for idx in (0..probes.len()).rev()`),
`build_0_build` (`part`, 8 RGs, `19.7 ms`) waits for `build_1` (`supplier`, 1
RG, `14.4 ms` on a single worker!) even though `part` has **zero** data or
dynamic-filter dependency on `nation -> supplier`. Overlapping independent leaf
builds (`part` || `nation -> supplier`) hides `supplier`'s `14.4 ms` single-RG
scan completely.

## 7. Reproduction Commands

All supporting scripts and the exact disposable scratch patch live under
`benchmarks/morsel_stock_gap_analysis/q14_q17_q20/`:

- `profile_q14_q17_q20.py` — captures side-by-side `EXPLAIN` / `EXPLAIN ANALYZE
VERBOSE`, warm-cache `mincore` verification, Arm PMUv3 `perf stat`, and 3,999
  Hz `perf record` symbol breakdowns.
- `run_ablations.py` — runs counterbalanced quiet-host ablation sweeps with
  exact Arrow IPC parity assertions against `stock_pushdown`.
- `scratch_ablations.patch` — exact env-gated scratch patch applied in a
  disposable detached worktree outside Git.

```bash
set -euo pipefail
work="$HOME/.cache/issue215"
mkdir -p "$work"
py="$HOME/.cache/issue189/venv/bin/python"
data="$HOME/.cache/issue189/tpch_sf5"

perf_lib="$perf_root/usr/lib/aarch64-linux-gnu"

taskset -c 0-7 "$py" -B "$analysis/profile_q14_q17_q20.py" explain \
  --runner "$base_runner" --data-dir "$data" --out-dir "$work/explain" \
  --queries q14,q17,q20 --arms stock_pushdown,morsel_pushdown --threads 8
```
