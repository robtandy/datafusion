# Morsel vs. Stock Pushdown Gap Analysis: TPC-H SF5 Q14, Q17, and Q20 (#215)

This diagnostic report isolates every millisecond of the remaining SF=5
warm-cache wall-time gap between single-config **Morsel (`morsel_pushdown`,
`morsel_mode=required`)** and **Stock DataFusion (`stock_pushdown`,
`morsel_mode=off`)** on **TPC-H Q14, Q17, and Q20** after Wave-4 (`#209`). Every
root cause is verified with side-by-side `EXPLAIN` / `EXPLAIN ANALYZE VERBOSE`
metrics, Arm PMUv3 hardware counters (`perf stat`), 3,999 Hz leaf CPU profiles
(`perf record`), and **counterbalanced quiet-host disposable scratch ablations**
(100% warm Linux page cache via `mincore`, 100% lossless Arrow IPC parity).

## Executive Summary

In Wave-4 (`benchmarks/morsel_tpch/sf5_22q_wave4_scorecard.md`),
`morsel_pushdown` trailed `stock_pushdown` by **`+40.5 ms` on `q14`** (`341.1`
vs. `300.6 ms`), **`+31.8 ms` on `q17`** (`499.8` vs. `468.0 ms`), and
**`+6.7 ms` on `q20`** (`329.3` vs. `322.6 ms`) — **`+79.0 ms`** combined.

Clean quiet-host measurements (`rob-tandy-dduck2`, 8 pinned Neoverse-N1 cores
`taskset -c 0-7`, `93–99%` host idle pre/post) reproduce those exact baselines
and prove that **six concrete, low-risk fixes not only close all three gaps vs.
`stock_pushdown`, but push `morsel_pushdown` ahead of BOTH `stock_pushdown` AND
DuckDB 2.0.1 on all three queries**:

### Root Causes at a Glance

1. **Q17 (+39.2 ms repro / +31.8 ms Wave-4): `is_infallible_expr` bug triggers
   `eval_staged` copy + scalar bit-scatter over 60M rows.**
   `datafusion/datasource-parquet/src/row_filter.rs::is_infallible_expr` does
   not recognize `JoinBloomFilterExpr`, so `l_partkey >= 2409 AND l_partkey <=
998971` (99.66% pass rate!) and `morsel_bloom_filter(l_partkey)` run via
   `DatafusionArrowPredicate::eval_staged`. On almost every 8,192-row batch
   across 60M rows, `eval_staged` allocates and copies 99.66% of `l_partkey` via
   `filter_record_batch` and scatters the result bit-by-bit in a scalar loop
   (`BooleanArray::value` `9.67%` + `DatafusionArrowPredicate::evaluate` `5.08%`
   - extra `__memcpy_generic` `1.65%` = **`16.4%` / `1.33G` wasted user
     cycles**). Morsel's L1-resident split-block Bloom filter is **already faster
     than Stock's `HashTableLookupExpr` (`Lookup::Routed`)** — fixing
     `is_infallible_expr` alone cuts Q17 by **`−84.6 ms` (`500.5 → 415.9 ms`)**,
     dropping `row_pushdown_eval_time` from `1,130 ms → 529 ms` (vs. Stock's
     `839 ms`).
2. **Q14 (+49.8 ms repro / +40.5 ms Wave-4): Wrong build side (`part` 1M rows
   vs. filtered `lineitem` 374.2K rows) + cross-core atomic Bloom build
   contention (`__aarch64_ldset4_relax`).**
   Stock DataFusion beats **both** Morsel (`341.1 ms`) **and** DuckDB 2.0.1
   (`336.5 ms`) on Q14 because Stock is the only engine that applies Parquet
   min/max interval selectivity (`l_shipdate` 1-month window ≈ `1.19%` → `~357K`
   rows < `part`'s `1.0M` rows) to build on **filtered `lineitem`** (no string
   columns, 2.67× smaller hash table, 68.8% of `part` pruned before decoding
   `p_type`, zero dynamic filter on 30M `lineitem` rows). Both Morsel
   (`pipeline_filter_shift` assumes 50% selectivity for a single-column range)
   and DuckDB build on unfiltered `part` (1M rows). Worse, Morsel then builds a
   useless 2 MiB `AtomicSplitBlockBloomFilter` across 8 cores with LSB-indexed
   atomic `fetch_or` (`__aarch64_ldset4_relax`: **`4.73%` of all Q14 cycles**,
   `+8.65M` L2D refills, `join_finalize = 37.9 ms` wall) and pushes it onto 30M
   `lineitem` rows where it prunes **0 rows** (`predicate_cache_inner_records =
29.61M`, `row_pushdown_eval_time = 71.4 ms` vs. Stock `28.0 ms`). Switching
   to Parquet-statistics interval selectivity (`+stats_build`), fixing a wave-1
   `AdaptiveRowFilter` `BulkDecode` dispatch bug (`buffered.rs:604`), and
   making radix Bloom filters MSB-indexed non-atomic drops Q14 to **`274.4 ms`**
   (with `ra2x`).
3. **Q20 (+1.6 ms repro / +6.7 ms Wave-4): Missing transitive equijoin
   `s_suppkey` dynamic filter on `lineitem` (`stage_0`) + sequential single-RG
   `supplier` build.**
   In `datafusion/core/src/morsel/parquet.rs::remap_probe_key_to_scan`,
   tracing `supplier`'s `s_suppkey` dynamic filter (`2,028` keys, `4%`
   selectivity) backward through `partsupp`'s `BuildSemi` join bails at
   `mid_probe.needs_build_emission()` and `JoinOutputCol::Build(_)`, even though
   `ps_suppkey == l_suppkey` is an exact equijoin key. Consequently, `lineitem`
   only receives `partsupp`'s composite `(l_partkey, l_suppkey)` Bloom filter
   plus loose `[min, max]` bounds, forcing `l_partkey` (`153.6 MB` compressed)
   to be decoded and hashed for **4.28M rows instead of 170K rows** and
   inflating `predicate_cache_records` **18.5×** (`46.07M` vs. Stock `2.41M`).
   Enabling equijoin substitution drops `predicate_cache_records` `46.07M →
2.49M` and saves **`−16.2 ms`** immediately (`324.4 → 308.2 ms`).
   Additionally, Morsel runs `nation -> supplier` (`14.4 ms` on 1 RG, 7 cores
   idle) **serially** before `part` (`19.7 ms`), whereas Stock runs them
   concurrently (`24.6 ms` combined vs. Morsel's `34.1 ms`).
4. **All three queries (`−16` to `−21 ms` each, `−54.1 ms` combined): Two-phase
   `RowFilter` ready-queue slot starvation (`ready_wait`).**
   `datafusion/core/src/morsel/parquet.rs:565` sizes the shared `ready::channel`
   slot semaphore to `read_ahead = workers = 8`. Under two-phase `RowFilter`
   I/O, a row group holds one of those 8 permits across Phase-1 I/O, ready
   queueing, worker `RowFilter` evaluation, Phase-2 I/O (`spawn_blocking`
   `get_ranges`), and post-Phase-2 queueing — structurally starving 8 workers
   (`peak_ready_depth = 4–6` < 8 workers, `ready_wait = 106–198 ms`). Doubling
   `chan_cap` to `read_ahead * 2 = 16` for pushed-filter scans cuts `ready_wait`
   by **55–68%** (`106 → 34 ms` on Q14, `160 → 73 ms` on Q17, `198 → 83 ms` on
   Q20) and saves **`−21.1 ms` (Q14), `−17.0 ms` (Q17), and `−16.0 ms` (Q20)**
   in pure wall time.

### 2.3 Accounting for `#138` `Agg fin / other` (`74.1 / 86.7 / 89.1 ms` in Wave-4)

In the Wave-4 scorecard, `Agg fin / other` is computed as the residual
`exec_ms − (decode_ms + process_ms) / 8 − join_fin_ms − sort_fin_ms`. Actual
`AggregateSink::finalize` on Q14 (`1` ungrouped row), Q17 (`1,021` + `1` rows),
and Q20 (`1,210` rows) takes **`< 1 ms`**. Our quiet-host traces prove this
`74–89 ms` residual consists of **three measurable terms**:

1. **`morsel_pending_io` (`spawn_blocking` `LocalFileSystem::get_ranges`):**
   Reading `347–513 MB` of column chunks from the Linux page cache into user
   buffers runs on Tokio blocking threads **sharing the same 8 pinned cores**
   outside worker `decode`/`process` clocks (`pending_io = 320.3 ms` Q14,
   `596.1 ms` Q17, `331.4 ms` Q20; `exec_cpu − (decode + proc)` is `~290–350 ms`
   CPU = **`~36–44 ms` wall** across 8 cores, matching Stock's own `ObjectStore`
   copy cost).
2. **Parallel `join_finalize` CPU vs. wall (`q14` only):** `join_finalize_work_ms`
   records wall duration (`37.9 ms`), whereas its 8 spawned radix finalize tasks
   burn `~250 ms` CPU (`~31 ms` wall of 8-core work).
3. **`ready_wait / 8` + sequential pipeline transition/tail-skew gaps:**
   `ready_wait / 8` accounts for **`13.2 ms`** (Q14), **`20.0 ms`** (Q17), and
   **`20.2 ms`** (Q20), driven directly by 2-phase `RowFilter` semaphore
   starvation (`slots = 8` for 8 workers) and serial single-RG pipelines (Q20's
   `supplier` 1 RG = `14.4 ms` wall with 7 workers idle). Doubling `slots` to
   `16` (`ra2x`) immediately recovers **`16–21 ms` wall** across all three
   queries.

## 3. Deep Dive: TPC-H Q14 (`344.7` vs. `294.9 ms`, `+49.8 ms` / Wave-4 `+40.5 ms`)

### 3.1 Why `stock_pushdown` Beats Both Morsel and DuckDB 2.0.1

Comparing all three engines' physical plans explains why `stock_pushdown`
(`300.6 ms` Wave-4 / `294.9 ms` repro) beats both `morsel_pushdown` (`341.1 ms`)
and **DuckDB 2.0.1 (`336.5 ms`)**:

- **`stock_pushdown`:** Uses `FilterExec`'s interval analysis
  (`datafusion_physical_expr::analyze`) over Parquet footer min/max column
  statistics (`l_shipdate` spans 7 years `1992-01-02..1998-12-01` → 1-month
  selectivity `~1.19%` → `~357K` estimated rows < `part`'s `1,000K` rows). Stock
  places **filtered `lineitem` (`374.2K` rows, fixed-width numerics only)** on
  the **build side** of a `Partitioned` `HashJoinExec` (`8 × 46.8K` L2-resident
  partitions, `build_time = 12.8 ms` CPU / **`1.6 ms` wall**), and scans `part`
  on the **probe side** with `DynamicFilter [p_partkey >= 3 AND <= 999996 AND
hash_lookup]`. Stock's `HashTableLookupExpr` **reuses the already-built hash
  tables at zero extra build cost**, pruning **68.8% of `part`** (`687.7K` rows)
  before decoding `p_type`, while `lineitem` executes **zero** dynamic join
  filters (`row_pushdown_eval_time = 27.99 ms`, `predicate_cache_inner_records
= 0`). Stock's timeline: `lineitem` + build `[0.2..243.6 ms]` (`243.4 ms`) +
  `part` + probe + agg `[244.0..266.7 ms]` (`22.7 ms`).
- **DuckDB 2.0.1 (`EXPLAIN`):** Estimates `~5,999,958` rows for filtered
  `lineitem` (generic 20% selectivity heuristic) vs. `~1,000,000` rows for
  `part`, so DuckDB **also** builds on unfiltered `part` (1M rows) and probes
  with `lineitem`.
- **`morsel_pushdown`:** `estimate_join_side_size` (`datafusion/core/src/morsel.rs:312`)
  estimates `lineitem` as `file_bytes * 4 >> shift` where `pipeline_filter_shift`
  assigns `shift = 1` (50% selectivity) for any non-equality predicate on one
  column → **`1,876 MB` vs. `part`'s `95.6 MB`** (off by **~50×**!). Morsel
  therefore builds on **unfiltered `part` (1M rows including variable-width

### 3.3 Why `AtomicSplitBlockBloomFilter` Burned 4.73% of All Q14 Cycles

In `datafusion/core/src/morsel/hash_join.rs::finalize_radix_all_in_memory`, 8
workers process 64 radix partitions partitioned by the **top 6 bits** of the
64-bit hash (`h >> 58`). Yet `AtomicSplitBlockBloomFilter::insert`
(`join_filter.rs:197`) indexes blocks by the **low bits** (`(h as usize) &
block_mask`) using atomic `word.fetch_or(bit, Ordering::Relaxed)`. Every worker
therefore collides on random cache lines across the entire 2 MiB Bloom array,
triggering 8M atomic `LDSET` instructions, `+8.65M` extra L2D refills, and
collapsing IPC from `2.41 → 2.05`. Simply switching `SplitBlockBloomFilter` to
**MSB-indexed blocks** (`(h >> (64 - block_bits))`, intra-block bits from low 32
bits) makes each radix partition own a disjoint contiguous slice of blocks
(`num_blocks >= 64`), eliminating atomic RMWs and cross-core cache-line bouncing
completely.

### 4.2 The Smoking Gun: `is_infallible_expr` → `eval_staged` Over 60M Rows

Why did Morsel spend **`1,130 ms`** in `row_pushdown_eval_time` across the two
`lineitem` scans vs. Stock's `836 ms` (`282 + 554 ms`) — even though Morsel's
`1,021`-key `SplitBlockBloomFilter` is a **2 KiB L1d-resident** filter?

In `datafusion/datasource-parquet/src/row_filter.rs:249`, `is_infallible_expr`
only recognizes built-in `datafusion-physical-expr` types; it cannot downcast
to `datafusion-core`'s `JoinBloomFilterExpr`, so it returns **`false`**. In
`prebuild_row_filter_candidates_with_grouping`, `l_partkey >= 2409 AND
l_partkey <= 998971` becomes `physical_exprs[0]` and
`morsel_bloom_filter(l_partkey)` is staged as `physical_exprs[1]`. Because
`[2409, 998971]` passes **99.66%** of rows (`surviving != num_rows` on almost
every 8,192-row batch), `DatafusionArrowPredicate::eval_staged`
(`row_filter.rs:161–196`) runs on **every batch of all 60,000,000 rows**:

1. `filter_record_batch(batch, &mask)` allocates and `memcpy`s 99.66% of the
   `l_partkey` array (~480 MB copied).
2. Evaluates `JoinBloomFilterExpr` on `sub_batch`.
3. Executes a **scalar `for row_idx in 0..num_rows` loop** calling
   `mask.is_valid(row_idx) && mask.value(row_idx)` and `builder.set_bit(...)`
   across **all 60,000,000 rows**.

## 5. Deep Dive: TPC-H Q20 (`324.4` vs. `322.8 ms`, `+1.6 ms` / Wave-4 `+6.7 ms`)

### 5.1 Root Cause 1: Missing Transitive `s_suppkey` Dynamic Filter on `stage_0` (`lineitem`)

Inspecting `RowFilter` candidates on `stage_0` (`lineitem`) exposed a major
propagation gap between Stock and Morsel:

- **`stock_pushdown` `lineitem` predicate:**
  `l_shipdate >= 1994-01-01 AND l_shipdate < 1995-01-01 AND DynamicFilter [
l_partkey >= 2217 AND l_partkey <= 999745 AND l_suppkey >= 13 AND l_suppkey
<= 49855 AND hash_lookup ] AND DynamicFilter [ l_suppkey >= 13 AND l_suppkey
<= 49941 AND hash_lookup ]`.
  Stock pushes **both** `partsupp`'s composite `(l_partkey, l_suppkey)` filter
  **and** `supplier`'s single-column `l_suppkey` filter (`2,028` keys, **`4.0%`
  selectivity**) onto `lineitem`. Execution order: `l_shipdate` (`46.5 MB`,
  `14.3%` → `4.3M` rows) → **`l_suppkey` `hash_lookup` (`85.7 MB`, `4%` → `170K`
  rows!)** → composite `(l_partkey, l_suppkey)` on only `170K` rows. Total
  `predicate_cache_records = 2.41M`.
- **`morsel_pushdown` `lineitem` `[rf-plan]`:**
  `#0 l_shipdate` (`2.9 MB/file`) → `#2 l_suppkey >= 13 AND <= 49855` (`5.4 MB`,
  **99.7% pass, NO Bloom!**) → `#1 l_partkey >= 2217 AND <= 999745` (`9.6 MB`,
  **99.8% pass, NO Bloom!**) → `#3 morsel_bloom_filter(l_partkey, l_suppkey)`
  (`15.0 MB`).
  Because `remap_probe_key_to_scan` (`datafusion/core/src/morsel/parquet.rs:1302`)
  returns `Ok(None)` whenever an intermediate join has
  `mid_probe.needs_build_emission()` (`BuildSemi` on `partsupp`) or emits
  `JoinOutputCol::Build(_)`, **`supplier`'s single-column `Bloom(s_suppkey)`
  never reaches `lineitem`**, even though `ps_suppkey == l_suppkey` is an exact
  equijoin key! As a result:
  1. `l_partkey` (`153.6 MB` compressed) and composite
     `morsel_bloom_filter(l_partkey, l_suppkey)` (`create_hashes`) evaluate over
     **4.28M rows instead of 170K rows (`25×` more rows!)**,
  2. `predicate_cache_records` explodes **19.1×** (`46.07M` vs. Stock `2.41M`),
  3. `perf record` confirms **`+99M` extra cycles in `__memcpy_generic`** (`5.05%`
     vs. `2.91%`), **`+58M` extra cycles in `filter_native::<i64>`** (`2.92%` vs.
     `1.68%`), and **`+4.70M` extra L2D refills** (`27.58M` vs. `22.88M`) —
     accounting for **100% of Q20's `+158M` cycle gap**.

Enabling equijoin key substitution across `Inner`/`BuildSemi` in
`remap_probe_key_to_scan` (`+q20_suppkey_push`, `DynF 12 → 15`) immediately
cuts `predicate_cache_records` from `46.07M → 2.49M`, cuts `stage_0` decode by
`−109 ms` CPU, and drops Q20 wall time by **`−16.2 ms` (`324.4 → 308.2 ms`)**,
already beating `stock_pushdown` (`322.8 ms`).

## 7. Reproduction Commands

All supporting scripts and the exact disposable scratch patch live under
`benchmarks/morsel_stock_gap_analysis/q14_q17_q20/`:

- `profile_q14_q17_q20.py` — captures side-by-side `EXPLAIN` / `EXPLAIN ANALYZE
VERBOSE`, warm-cache `mincore` verification, Arm PMUv3 `perf stat`, and 3,999
  Hz `perf record` symbol breakdowns.
- `run_ablations.py` — runs counterbalanced quiet-host ablation sweeps with
  exact Arrow IPC parity assertions against `stock_pushdown`.
- `scratch_ablations.patch` — exact env-gated scratch patch applied in a
  disposable detached worktree outside Git.

```bash
set -euo pipefail
work="$HOME/.cache/issue215"
mkdir -p "$work"
py="$HOME/.cache/issue189/venv/bin/python"
data="$HOME/.cache/issue189/tpch_sf5"
base_runner="$HOME/.cache/issue209/target/release-nonlto/examples/morsel_tpch_runner"
perf_root="$HOME/.cache/issue155.djRKpG/perf"
analysis="benchmarks/morsel_stock_gap_analysis/q14_q17_q20"

# 1. Capture side-by-side EXPLAIN, EXPLAIN ANALYZE VERBOSE, and measure JSONs.
taskset -c 0-7 "$py" -B "$analysis/profile_q14_q17_q20.py" explain \
  --runner "$base_runner" --data-dir "$data" --out-dir "$work/explain" \
  --queries q14,q17,q20 --arms stock_pushdown,morsel_pushdown --threads 8

# 2. Capture quiet-host Arm PMUv3 perf stat & 3,999 Hz perf record profiles.
taskset -c 0-7 "$py" -B "$analysis/profile_q14_q17_q20.py" perf \
  --runner "$base_runner" --data-dir "$data" --out-dir "$work/perf" \
  --perf "$perf_root/usr/lib/linux-tools-6.8.0-149/perf" \
  --perf-lib-dir "$perf_root/usr/lib/aarch64-linux-gnu" \
  --queries q14,q17,q20 --arms stock_pushdown,morsel_pushdown \
  --threads 8 --stat-repeats 5

# 3. Build disposable scratch ablation runner outside Git and run ablations.
git worktree add --detach "$work/scratch" HEAD
git -C "$work/scratch" apply "$(pwd)/$analysis/scratch_ablations.patch"
mkdir -p "$work/scratch/datafusion/core/examples"
cp benchmarks/morsel_tpch/tpch_runner.rs "$work/scratch/datafusion/core/examples/morsel_tpch_runner.rs"
(
  cd "$work/scratch"
  MORSEL_BENCH_REVISION="$(git rev-parse HEAD)" CARGO_TARGET_DIR="$work/target" \
    RUSTC_WRAPPER=sccache \
    timeout 30m cargo build --locked --profile release-nonlto -j 8 \
      -p datafusion --no-default-features \
      --features parquet,sql,datetime_expressions,unicode_expressions \
      --example morsel_tpch_runner
)
scratch_runner="$work/target/release-nonlto/examples/morsel_tpch_runner"

taskset -c 0-7 "$py" -B "$analysis/run_ablations.py" \
  --baseline-runner "$base_runner" --scratch-runner "$scratch_runner" \
  --data-dir "$data" --out-dir "$work/ablations" \
  --queries q14,q17,q20 --threads 8 --repeats 5

# 4. Clean up disposable worktree.
git worktree remove --force "$work/scratch"
```
