# Morsel vs. Stock Stock-Gap Root-Cause Diagnosis: TPC-H SF5 `q9`, `q10`, and `q13` (#214)

This report presents a surgical, evidence-backed root-cause breakdown of the
three largest remaining **Morsel (`morsel_pushdown` / `morsel_no_pushdown`) vs.
Stock (`stock_default` / `stock_pushdown`)** gaps on **TPC-H SF=5** after
Wave-4 (`#209`,
[sf5_22q_wave4_scorecard.md](../morsel_tpch/sf5_22q_wave4_scorecard.md)):

- **`q9`:** `morsel_pushdown` `1,414.4 ms` (W4 `1,397.5 ms`),
  `morsel_no_pushdown` `1,337.7 ms` (W4 `1,336.8 ms`) vs. **`stock_default`
  `1,028.0 ms`** (W4 `1,023.6 ms`) — **`+386.4 ms` (`1.38×`)** gap.
- **`q13`:** `morsel_pushdown` `612.6 ms` (W4 `590.7 ms`), `morsel_pruning`
  `556.8 ms` (W4 `562.5 ms`) vs. **`stock_default` `500.9 ms`** (W4
  `479.1 ms`) — **`+111.7 ms` (`1.22×`)** gap.
- **`q10`:** `morsel_pushdown` `610.0 ms` (W4 `616.0 ms`) vs.
  **`stock_pushdown` `522.1 ms`** (W4 `527.3 ms`) — **`+87.9 ms` (`1.17×`)**
  gap (already beats `stock_default` `654.7 ms`).

All baseline timings, `EXPLAIN ANALYZE VERBOSE` per-operator metrics,
`MORSEL_PHASE_TRACE` / `MORSEL_SUBPHASE_TRACE` wall timelines, Arm Neoverse-N1
PMUv3 hardware counters (`perf stat`), demangled leaf CPU profiles
(`perf record -F 3999 -e cycles:u`, zero lost samples), and parity-verified
disposable scratch ablations were collected on `rob-tandy-dduck2` (8 pinned
cores, 100% warm Linux page cache verified via `mincore`). Zero production Rust
or existing benchmark files were modified.

---

## Executive Summary of Findings

Six concrete, code-level bottlenecks explain virtually every millisecond of all
three gaps — and disposable scratch ablations already **eliminate 100% of the
Stock gap on `q13` (`−152.5 ms`, beating `stock_default` by `−45.9 ms`)**,
**89% of the gap on `q10` (`−91.6 ms`, landing within `11.5 ms` of
`stock_pushdown`)**, and **`−151.9 ms` on `q9` before even adding the two
largest `q9` algorithmic fixes (`part → partsupp` sibling pushdown and 2-key
`FlatIntPairTable`)**:

1. **Unfiltered Build Tables Construct Contended 8 MiB
   `AtomicSplitBlockBloomFilter`s That Prune 0% of Rows (`q9`, `q10`, `q13`) —
   `parquet.rs:896`, `join_filter.rs:191-198`:**
   - `parquet.rs:896` sets `build_bloom: any_pushdown` unconditionally for every
     join build regardless of whether the build pipeline has any selective
     filter.
   - During `finalize_radix_all_in_memory`, all 8 workers concurrently execute
     up to 8 `AtomicU32::fetch_or` (`__aarch64_ldset4_relax`) instructions per
     build row into a single shared `AtomicSplitBlockBloomFilter`.
   - On **`q9`**, unfiltered 4M-row `partsupp` (`build_2`) performs up to 32M
     cross-core atomic RMWs into an 8 MiB filter (**`+85–99 ms` wall in
     `join_finalize`**, **`+1.56 Gc`** CPU) and then evaluates that 0%-pruning
     filter on `lineitem`! **Crucially, this disproves the earlier Wave-4
     hypothesis that `#207` leaving `lineitem` in `RowFilter` caused `q9`'s
     `+60.7 ms` pushdown regression:** `lineitem`'s probe pipeline is actually
     **`−32.2 ms` faster** in `morsel_pushdown` (`967.0` vs. `999.2 ms`) thanks
     to `part`'s 5.44%-selective Bloom filter; skipping unfiltered Blooms
     immediately cuts `q9` by **`−129.2 ms` (`1,514.8 → 1,385.6 ms`)**, beating
     `morsel_no_pushdown` (`1,419.8 ms`).
   - On **`q13`** (`customer`, 750K rows) and **`q10`** (`customer`, 750K
     rows), building and probing a 100%-pass Bloom filter adds **`+17 ms` wall
     in `join_finalize`** + `0.45 Gc` (`q13`) / `0.21 Gc` (`q10`) in Bloom
     build/eval (`−63.5 ms` verified on `q13`, `−26.0 ms` on `q10`).
2. **58K Tiny 128-Row Radix `RecordBatch` Slices + Redundant Single-Threaded
   `.clone()` / `drop()` Storms (`q9`, `q13`, `q10`) — `radix_agg.rs:395`,
   `hash_join.rs:1487`, `morsel.rs:5015`:**
   - `RadixBuildStore::push_packed_batch` (`radix_join.rs:171`) and
     `RadixPartitionStore::push_partial_batch` (`radix_agg.rs:161`) emit 64
     tiny ~128-row `RecordBatch::slice` objects per 8,192-row input batch,
     accumulating **`58,560` batches** on `q9` `orders`, **`31,424` batches**
     on `q9` `partsupp`, and **`57,979` batches** on `q13` `c_custkey`
     `AggregateSink`.
   - In **`radix_agg.rs:395`**, `finalize_and_emit_radix` calls
     `store.mem_batches[p].clone()` (`15.6 ms` single-threaded!) and then
     immediately calls `drop(store)` (`14.6 ms` single-threaded!) — **`30.1 ms`
     of pure wasted single-threaded wall time on `q13`**, plus `71.3 ms`
     dropping/merging 57,979 tiny slices across 8 workers (accounting for the
     entire `101–103 ms` `agg_finalize` wall time despite only `0.41 Gc` of
     actual aggregate compute!).
   - In **`hash_join.rs:1487`**, `finalize_radix_all_in_memory` clones all
     `58,560` / `31,424` slices single-threaded (`~31 ms`) and drops them
     single-threaded (`45.6 + 27.0 = 72.6 ms`), and **`morsel.rs:5015`** then
     calls synchronous single-threaded `drop(finalized_tables)` on the critical
     path (**`43.0–56.6 ms` wall on `q9`**!). Moving ownership + parallel
     partition drop cuts `q9` `join_finalize` by **`−73.3 ms`** and `q13` wall
     time by **`−39.2 ms`** in scratch verification.
3. **Inverted Build-Side Selection on `q10` (`customer` 750K×7 wide cols vs.
   Filtered `orders` 286K×2 ints) — `morsel.rs:208-216, 246-290`:**
   - `pipeline_filter_shift` collapses both bounds of
     `o_orderdate >= '1993-10-01' AND o_orderdate < '1994-01-01'` onto one
     column entry with `weight = 1` (`÷2` = 50% vs. actual **3.8% = `÷26`**),
     and `estimate_side_size` uses raw whole-file `total_file_bytes()`
     (`orders` 234 MB vs. `customer` 45 MB), ignoring projection width
     (`orders` projects 2 `i64`s = 4.5 MB filtered vs. `customer`'s 7 columns
     including 5 wide strings = ~135 MB!).
   - Result: Morsel builds 750K-row `customer` (`162 ms` wall, 6 RGs across 8
     cores leaving 2 cores idle), prunes **0%** of `customer` (vs. Stock's
     **71.6% / 537K rows pruned**), and runs `gather_radix_build_column`
     (`0.78 Gc`, `9.28%` of `q10`!) twice across 5 wide `StringView` columns.
   - Fixing `estimate_join_side_size` in scratch ablation flips `q10` to build
     filtered `orders` first, collapsing `join_finalize` **`2.8×` (`108.0 →
38.1 ms`)** and cutting wall time by **`−91.6 ms` (`657.6 → 566.0 ms` vs.
     `stock_pushdown` `554.5 ms`)**!
4. **Redundant 64-Partition Build Key Gather (`c_custkey == o_custkey`) &
   Global Radix Probe Overhead on `q13` — `hash_join.rs:4780-4810, 6259`:**
   - On `q13`, `NOT LIKE '%special%requests%'` is identical between Stock
     (`1.31 Gc`) and Morsel (`1.29–1.33 Gc`), and Morsel's 750K-group
     `DirectGroupedState` aggregate actually uses **`4.5×` less CPU** than
     Stock's `SinglePartitioned AggregateExec` (`0.41` vs. `1.87 Gc`).
   - Instead, Morsel spends **`3.16 Gc` vs. Stock's `1.50 Gc` (`+1.66 Gc`)** in
     the `LEFT OUTER JOIN`: `probe_collect_radix_flat_int` (`2.20 Gc` probing
     64 global partitions randomly vs. Stock's 8 partition-local tables),
     **`gather_radix_build_column` (`0.68 Gc` / `8.2%` of total query cycles)**
     randomly gathering `c_custkey` from 64 `customer` partitions even though
     `c_custkey == o_custkey` is already in the probe batch, and atomic
     `mark_matched` (`0.28 Gc`).
   - Skipping redundant key gather alone cuts `q13` by **`−49.8 ms` (`−306 ms`
     CPU)**; combined with `NO_UNFILTERED_BLOOM` + `NO_RADIX_CLONE`, `q13`
     drops **`624.7 → 472.2 ms` (`−152.5 ms`)**, beating `stock_default`
     (`518.1 ms`) by **`−45.9 ms` (`0.91×`)**!
5. **Missing Sibling Dynamic Filter Propagation (`part → partsupp`) &
   `KeyKind::Rows` (`RowConverter` + `memcmp`) on `q9`'s 4M-Row `partsupp` —
   `morsel.rs:2455`, `parquet.rs:997`, `hash_join.rs:3205`:**
   - `run_build_pipelines` runs builds in reverse probe order (`nation → orders
→ partsupp → supplier → part`), so selective `part` (`54.4K / 1M` = 5.44%)
     builds **last**, and `push_filter_into_prefix` never propagates join-key
     equivalences (`p_partkey = l_partkey = ps_partkey`) to sibling builds.
     Pushing `part → partsupp` shrinks `partsupp` **`18×` (`4.0M → 218K`
     rows)**, saving **`~135–175 ms` wall** on `q9`.
   - Furthermore, `(ps_suppkey, ps_partkey)` falls into generic `KeyKind::Rows`
     (`arrow_row::RowConverter` + `memcmp`), burning **`2.01–2.26 Gc`** in
     `probe_step_key_candidates` (`1.37–1.50 Gc`) + `memcmp` (`0.64–0.76 Gc`).
     A specialized 2-key `FlatIntPairTable<(i64, i64)>` saves **`~65–85 ms`**.
6. **64-Way Radix Fragmentation of Small/Dense Integer Builds vs. Stock
   `ArrayMap` (`q9`, `q13`) — `radix_join.rs:30`:**
   - `RADIX_JOIN_THRESHOLD_ROWS = 16_384` shatters 54.4K-row `part`, 50K-row
     `supplier`, and 750K-row dense `customer` (`1..=750,000`) into 64 separate
     heap-allocated `SingleHashTable`s, causing **`+54%` more L2 cache refills**
     on `q9` `morsel_no_pushdown` (`170.3M` vs. Stock `110.5M`, dragging IPC
     `1.68 → 1.35`). Stock uses `ArrayMap` (direct $O(1)$ array lookup) on
     `supplier` and `nation` and partition-local tables on `orders`/`partsupp`.

## 2. Deep Dive: TPC-H `q9` (`+386 ms` vs. `stock_default`)

### 2.1 Physical Plan & Join Build/Probe Comparison

- **Stock (`stock_default`, `1,028.0 ms`, `7,241 ms` CPU):**
  - `lineitem` (30M rows, `456.3 MB`) probes `CollectLeft` `part` (`54.4K` rows
    after `p_name LIKE '%green%'`, reducing to `1.632M` rows) → `CollectLeft`
    `supplier` (`50K` rows, **`ArrayMap`**) → **`Partitioned` 8-way**
    `partsupp` (`4.0M` rows = `500K`/partition, built in parallel) →
    **`Partitioned` 8-way** `orders` (`7.5M` rows = `937.5K`/partition, built
    in parallel) → `CollectLeft` `nation` (`25` rows, **`ArrayMap`**) →
    `Partial`/`FinalPartitioned` `AggregateExec` (175 groups).
  - **Per-operator `elapsed_compute` (`EXPLAIN ANALYZE VERBOSE`):**
    - `DataSourceExec` sum: `4,133 ms` (`lineitem` `3,561 ms`, `partsupp`
      `235 ms`, `orders` `206 ms`, `part` `128 ms`, `supplier` `4 ms`, `nation`
      `2 ms`).
    - `HashJoinExec` sum: **`2,455.7 ms`** across all 5 joins:
      - `part ⋈ lineitem`: `build = 1.3 ms`, `join = 877.0 ms` (`30M → 1.63M`)
      - `supplier ⋈ ...`: `build = 0.3 ms`, `join = 56.4 ms` (`arr_map = 1`)
      - `partsupp ⋈ ...`: `build = 337.8 ms`, `join = 307.2 ms` (`4M` build,
        `1.63M` probe, 8-way partitioned)
      - `orders ⋈ ...`: `build = 608.4 ms`, `join = 241.1 ms` (`7.5M` build,
        `1.63M` probe, 8-way partitioned)
      - `nation ⋈ ...`: `build = 2.3 ms`, `join = 23.8 ms` (`arr_map = 1`)
    - `ProjectionExec` `58.7 ms`, `AggregateExec` `47.2 ms`, `FilterExec`
      `24.2 ms`.
- **Morsel (`morsel_no_pushdown` `1,337.7 ms` / `morsel_pushdown` `1,414.4 ms`):**
  - Executes **all 5 build pipelines strictly sequentially** in reverse probe
    order (`morsel.rs:2455`): `build_4` (`nation`) → `build_3` (`orders`, 7.5M
    rows, **64-way radix**) → `build_2` (`partsupp`, 4.0M rows, **64-way radix
    `KeyKind::Rows`**) → `build_1` (`supplier`, 50K rows, **64-way radix**) →
    `build_0` (`part`, 54.4K rows, **64-way radix**).
  - Then scans `lineitem` (30M rows) through 5 chained `HashJoinProbe`s →
    `Projection` → `AggregateSink` (175 groups).

## 5. Disposable Scratch Ablation Verification (Parity-Checked)

To verify our root causes directly before any production code changes, we added
five env-var-gated scratch toggles inside a disposable detached worktree
(`$HOME/.cache/issue214/diag_wt`):

- **`NO_UNFILT_BLOOM`**: Skip `build_bloom` when the build pipeline has no
  filter predicate (`pipeline_filter_shift == 0` and not a `Stage` source).
- **`NO_RADIX_CLONE`**: Replace `store.mem_batches[p].clone()` with
  `std::mem::take` in `radix_agg.rs:395`, and move per-partition build slices
  into worker-owned slots in `hash_join.rs:1487` so workers drop slices in
  parallel instead of single-threaded clone + drop.
- **`ASYNC_DROP`**: Offload `drop(finalized_tables)` (`morsel.rs:5015`) off the
  critical path via `spawn_blocking`.
- **`FIX_BUILD_EST`**: Give two-sided range predicates on the same column
  (`>= AND <`) `weight = 4` (instead of `1`) and scale `Parquet` side estimates
  by projected column width (flipping `q10` to build filtered `orders` first).

  key columns (`c_custkey == o_custkey` on `q13`) from the probe batch via
