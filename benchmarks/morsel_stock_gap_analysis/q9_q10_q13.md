# Morsel vs. Stock Stock-Gap Root-Cause Diagnosis: TPC-H SF5 `q9`, `q10`, and `q13` (#214)

This report presents a surgical, evidence-backed root-cause breakdown of the
three largest remaining **Morsel (`morsel_pushdown` / `morsel_no_pushdown`) vs.
Stock (`stock_default` / `stock_pushdown`)** gaps on **TPC-H SF=5** after
Wave-4 (`#209`,
[sf5_22q_wave4_scorecard.md](../morsel_tpch/sf5_22q_wave4_scorecard.md)):

- **`q9`:** `morsel_pushdown` `1,414.4 ms` (W4 `1,397.5 ms`),
  `morsel_no_pushdown` `1,337.7 ms` (W4 `1,336.8 ms`) vs. **`stock_default`
  `1,028.0 ms`** (W4 `1,023.6 ms`) — **`+386.4 ms` (`1.38×`)** gap.
- **`q13`:** `morsel_pushdown` `612.6 ms` (W4 `590.7 ms`), `morsel_pruning`
  `556.8 ms` (W4 `562.5 ms`) vs. **`stock_default` `500.9 ms`** (W4
  `479.1 ms`) — **`+111.7 ms` (`1.22×`)** gap.
- **`q10`:** `morsel_pushdown` `610.0 ms` (W4 `616.0 ms`) vs.
  **`stock_pushdown` `522.1 ms`** (W4 `527.3 ms`) — **`+87.9 ms` (`1.17×`)**
  gap (already beats `stock_default` `654.7 ms`).

All baseline timings, `EXPLAIN ANALYZE VERBOSE` per-operator metrics,
`MORSEL_PHASE_TRACE` / `MORSEL_SUBPHASE_TRACE` wall timelines, Arm Neoverse-N1
PMUv3 hardware counters (`perf stat`), demangled leaf CPU profiles
(`perf record -F 3999 -e cycles:u`, zero lost samples), and parity-verified
disposable scratch ablations were collected on quiet `rob-tandy-dduck2`
(`taskset -c 0-7`, 100% warm Linux page cache verified via `mincore`). Zero
production Rust or existing benchmark files were modified; all supporting
patches and scripts live under
[`q9_q10_q13/`](q9_q10_q13/) (`diag_and_ablations.patch`,
`morsel_diag_runner.rs`, `run_ablations.py`, `profile_perf.py`).

## Executive Summary of Findings

Six concrete, code-level bottlenecks explain virtually every millisecond of all
three gaps — and parity-verified quiet-host scratch ablations on
`taskset -c 0-7` already **eliminate 100% of the Stock gap on `q13`
(`−137.6 ms`, beating `stock_default` by `−12.0 ms`)**, **93% of the gap on
`q10` (`−75.9 ms`, landing within `5.4 ms` of `stock_pushdown`)**, and cut
`q9` by **`−163.5 ms`** via `+NO_UNFILT_BLOOM` alone (`1,433.1 → 1,269.6 ms`,
and `1,165.4 ms` query-clock wall with `+ALL_Q9_FIXES`, which includes
`ASYNC_DROP` teardown deferral; see §5) before even adding the two largest `q9`
algorithmic fixes (`part → partsupp` sibling pushdown and 2-key
`FlatIntPairTable`):

1. **Unfiltered Build Tables Construct Contended 8 MiB
   `AtomicSplitBlockBloomFilter`s That Prune 0% of Rows (`q9`, `q10`, `q13`) —
   `parquet.rs:896`, `join_filter.rs:191-198`:**
   - `parquet.rs:896` sets `build_bloom: any_pushdown` unconditionally for every
     join build regardless of whether the build pipeline has any selective
     filter.
   - During `finalize_radix_all_in_memory`, all 8 workers concurrently execute
     up to 8 `AtomicU32::fetch_or` (`__aarch64_ldset4_relax`) instructions per
     build row into a single shared `AtomicSplitBlockBloomFilter`.
   - On **`q9`**, unfiltered 4M-row `partsupp` (`build_2`) performs up to 32M
     cross-core atomic RMWs into an 8 MiB filter (**`+84.3 ms` wall in
     `build_2.finalize`**, **`+1.56 Gc`** build CPU) and then evaluates that
     0%-pruning filter on `lineitem`. **Crucially, the 5-repeat ablation in §5
     disproves the earlier Wave-4 hypothesis that `#207` leaving `lineitem` in
     `RowFilter` caused `q9`'s `+60.7 ms` pushdown regression:** skipping
     unfiltered Blooms while keeping `lineitem` in `RowFilter` (`RF=245/4`)
     cuts `q9` by **`−163.5 ms` (`1,433.1 → 1,269.6 ms`)**, decisively beating
     `morsel_no_pushdown` (`1,341.9 ms`) by **`−72.3 ms`** (`−1,118 ms` exec
     CPU).
   - On **`q13`** (`customer`, 750K rows) and **`q10`** (`customer`, 750K
     rows), building and probing a 100%-pass Bloom filter adds **`+16.8 ms`
     wall in `stage_0_build.finalize`** (`q13`, single-run trace in §3.2) and
     `0.75 Gc` total (`0.45 Gc` eval + `0.31 Gc` build) on `q13`, and `0.21 Gc`
     `ldset4` on `q10`. In the 5-repeat §5 ablation (`+NO_UNFILT_BLOOM`),
     skipping `customer`'s unfiltered Bloom saves **`−60.6 ms`** on `q13`
     (`jf 26.2 → 9.3 ms`) and **`−18.5 ms`** on `q10` (`build_0_build` `jf`
     `73.8 → 68.0 ms`, total `jf` `96.5 → 92.2 ms`).
2. **58K Tiny 128-Row Radix `RecordBatch` Slices + Redundant Single-Threaded
   `.clone()` / `drop()` Storms (`q9`, `q13`, `q10`) — `radix_agg.rs:389, 404`,
   `hash_join.rs:1497`, `morsel.rs:4998`:**
   - `RadixBuildStore::push_packed_batch` (`radix_join.rs:171`) and
     `RadixPartitionStore::push_partial_batch` (`radix_agg.rs:161`) emit 64
     tiny ~128-row `RecordBatch::slice` objects per 8,192-row input batch,
     accumulating **`58,496–58,560` batches** on `q9` `orders`,
     **`31,424–31,488` batches** on `q9` `partsupp`, and **`57,979` batches**
     on `q13` `c_custkey` `AggregateSink`.
   - In **`radix_agg.rs:389`**, `finalize_and_emit_radix` calls
     `store.mem_batches[p].clone()` (`15.1–15.4 ms` single-threaded) and then
     immediately calls `drop(store)` at **`radix_agg.rs:404`** (`14.2–14.5 ms`
     single-threaded) — **`29.3–30.0 ms` of pure wasted single-threaded wall
     time on `q13`**, plus `66.0–75.1 ms` dropping/merging 57,979 tiny slices
     across 8 workers (accounting for the entire `95.3–105.1 ms` `agg_finalize`
     wall time despite only `0.41–0.42 Gc` of actual aggregate compute).
   - In **`hash_join.rs:1497`**, `finalize_radix_all_in_memory` clones all
     `58,496` / `31,424` slices single-threaded (`19.9 + 8.8 = 28.7 ms`) and
     drops them single-threaded (`42.4 + 25.1 = 67.5 ms`), and
     **`morsel.rs:4998`** then calls synchronous single-threaded
     `drop(finalized_tables)` on the critical path (**`55.0–58.4 ms` wall on
     `q9`**). In quiet-host `taskset -c 0-7` verification, moving ownership
     with per-worker drop (`+NO_RADIX_CLONE`) reduces `q13` wall by
     **`−46.5 ms`**, and cuts `q9` `join_finalize` by `−77.5 ms` (`−63.2 ms`
     wall in §5), **but increases `q9` exec CPU (`9,302 → 9,482 ms`,
     `+180 ms`) via higher `lineitem` `decode_work` (`5,246 → 5,430 ms`) — a
     risk for Fix 2(b) that can offset much of the `join_finalize` gain on
     other hosts** (see §5 and §6 Rank #2). Deferring `drop(finalized_tables)`
     via `spawn_blocking` (`+ASYNC_DROP`) lowers `q9`'s reported query-clock
     wall by `−74.2 ms` (`+ALL_Q9_FIXES` reaches `1,165.4 ms`), but is
     **teardown deferral** rather than a process-wall saving; reducing slice
     count via coalescing (Fix 2d) and parallelizing drop (Fix 2c, unverified)
     are needed for genuine compute/process-wall wins.
3. **Inverted Build-Side Selection on `q10` (`customer` 750K×7 wide cols vs.
   Filtered `orders` 286K×2 ints) — `morsel.rs:208-216, 246-290`:**
   - `pipeline_filter_shift` collapses both bounds of
     `o_orderdate >= '1993-10-01' AND o_orderdate < '1994-01-01'` onto one
     column entry with `weight = 1` (`÷2` = 50% vs. actual **3.8% = `÷26`**),
     and `estimate_side_size` uses raw whole-file `total_file_bytes()`
     (`orders` 234 MB vs. `customer` 45 MB), ignoring projection width
     (`orders` projects 2 `i64`s = 4.5 MB filtered vs. `customer`'s 7 columns
     including 4 wide strings `c_name`, `c_address`, `c_phone`, `c_comment`
     ≈ 135 MB).
   - Result: Morsel builds 750K-row `customer` (`163.1 ms` wall, 6 RGs across 8
     cores leaving 2 cores idle), prunes **0%** of `customer` (vs. Stock's
     **71.6% / 537K rows pruned**), and runs `gather_radix_build_column`
     (`0.78 Gc`, `9.28%` of `q10`) twice across those 4 wide `StringView`
     columns.
   - Fixing `estimate_join_side_size` in scratch ablation flips `q10` to build
     filtered `orders` first, collapsing `join_finalize` **`2.6×` (`96.5 →
36.7 ms`)** and cutting wall time by **`−74.3 ms` (`606.9 → 532.6 ms`,
     and `531.0 ms` with `+ALL_Q10_FIXES` vs. `stock_pushdown` `525.6 ms`)**.
4. **Redundant 64-Partition Build Key Gather (`c_custkey == o_custkey`) &
   Global Radix Probe Overhead on `q13` — `hash_join.rs:4780-4810, 6259`:**
   - On `q13`, `NOT LIKE '%special%requests%'` is identical between Stock
     (`1.31 Gc`) and Morsel (`1.29–1.33 Gc`), and Morsel's 750K-group
     `DirectGroupedState` aggregate actually uses **`4.5×` less CPU** than
     Stock's `SinglePartitioned AggregateExec` (`0.41–0.42` vs. `1.87 Gc`).
   - Instead, Morsel spends **`3.16 Gc`** (`morsel_no_pushdown`) / **`2.43 Gc`**
     (`morsel_pushdown`, excluding `0.75 Gc` Bloom) vs. Stock's **`1.51 Gc`**
     (`0.85` `JoinHashMapU32` + `0.53` `equal_rows_single_col` + `0.12`
     `hash_single_array`) in the `LEFT OUTER JOIN`: `probe_collect_radix_flat_int`
     (`2.20 / 1.45 Gc` probing 64 global partitions randomly vs. Stock's 8
     partition-local tables), **`gather_radix_build_column` (`0.68 Gc` / `8.2%`
     of total query cycles)** randomly gathering `c_custkey` from 64 `customer`
     partitions even though `c_custkey == o_custkey` is already in the probe
     batch, and atomic `mark_matched` (`0.28–0.30 Gc`).
   - Skipping redundant key gather alone cuts `q13` by **`−57.2 ms`**
     (`−316 ms` CPU); combined with `NO_UNFILT_BLOOM` + `NO_RADIX_CLONE`, `q13`
     drops **`611.9 → 474.3 ms` (`−137.6 ms`)**, beating `stock_default`
     (`486.3 ms`) by **`−12.0 ms` (`0.98×`)**.
5. **Missing Sibling Dynamic Filter Propagation (`part → partsupp`) &
   `KeyKind::Rows` (`RowConverter` + `memcmp`) on `q9`'s 4M-Row `partsupp` —
   `morsel.rs:2455`, `parquet.rs:997`, `hash_join.rs:3205`:**
   - `run_build_pipelines` runs builds in reverse probe order (`nation → orders
→ partsupp → supplier → part`), so selective `part` (`54.4K / 1M` = 5.44%)
     builds **last**, and `push_filter_into_prefix` never propagates join-key
     equivalences (`p_partkey = l_partkey = ps_partkey`) to sibling builds.
     Pushing `part → partsupp` shrinks `partsupp` **`18×` (`4.0M → 218K`
     rows)**, with an unverified estimated saving of **`~135–175 ms` wall** on
     `q9`.
   - Furthermore, `(ps_suppkey, ps_partkey)` falls into generic `KeyKind::Rows`
     (`arrow_row::RowConverter` + `memcmp`), burning **`2.10 Gc`** in
     `morsel_pushdown` (`1.37` `probe_step_key_candidates` + `0.64` `memcmp` +
     `0.09` `arrow_row::Rows::row`) and **`2.37 Gc`** in `morsel_no_pushdown`
     (`1.50 + 0.76 + 0.12`). A specialized 2-key `FlatIntPairTable<(i64, i64)>`
     has an unverified estimated saving of **`~65–85 ms`**.
6. **64-Way Radix Fragmentation of Small/Dense Integer Builds vs. Stock
   `ArrayMap` (`q9`, `q13`) — `radix_join.rs:30`:**
   - `RADIX_JOIN_THRESHOLD_ROWS = 16_384` shatters 54.4K-row `part`, 50K-row
     `supplier`, and 750K-row dense `customer` (`1..=750,000`) into 64 separate
     heap-allocated `SingleHashTable`s, causing **`+54%` more L2 cache refills**
     on `q9` `morsel_no_pushdown` (`170.2M` vs. Stock `110.3M`, dragging IPC
     `1.63 → 1.19`). Stock uses `ArrayMap` (direct $O(1)$ array lookup) on
     `supplier` and `nation` and partition-local tables on `orders`/`partsupp`.

## 2. Deep Dive: TPC-H `q9` (`+386 ms` vs. `stock_default`)

### 2.1 Physical Plan & Join Build/Probe Comparison

- **Stock (`stock_default`, `1,028.0 ms`, `7,241 ms` CPU):**

### 2.4 Why `#207`'s Adaptive Controller Left `lineitem` in `RowFilter` (`245 RF / 4 Bulk`)

The adaptive controller (`buffered.rs:740-790`) measures per-RG
`(decode + process + RowFilter)` CPU + `0.5 ns/byte` I/O. On `q9` `lineitem`,
`RowFilter` with `part`'s 5.44%-selective Bloom filter cuts `probe` pipeline
`decode + process` from `3,600 + 3,723 = 7,323 ms` (`30.5 ms/RG`) down to
`4,525 + 1,964 = 6,489 ms` (`27.0 ms/RG`) and cuts `probe_collect_radix_flat_int`
by `−3.25 Gc` (while the single-run `main.probe` delta of `−4.4 ms` in §2.2 is
within single-run noise). The decisive proof that `#207` made the right choice
for `lineitem` is the **5-repeat ablation in §5**: once unfiltered `partsupp`
and `supplier` Blooms are skipped (`+NO_UNFILT_BLOOM`), `morsel_pushdown` keeps
`lineitem` in `RowFilter` (`RF=245/4`) and drops to **`1,269.6 ms`** — beating
`morsel_no_pushdown` (`1,341.9 ms`) by **`−72.3 ms`** (`−1,118 ms` exec CPU).
The `+65 to +91 ms` baseline regression of `morsel_pushdown` over
`morsel_no_pushdown` came from **`build_2` (`partsupp`) building and probing a
useless 8 MiB `AtomicSplitBlockBloomFilter` (`+84.3 ms` wall in
`build_2.finalize`)**, not from `#207` leaving `lineitem` in `RowFilter`.

## 5. Quiet-Host Disposable Scratch Ablation Verification (Parity-Checked)

To verify our root causes directly before any production code changes, we
packaged five env-var-gated scratch toggles into
[`q9_q10_q13/diag_and_ablations.patch`](q9_q10_q13/diag_and_ablations.patch)
(applied only in a disposable detached worktree):

- **`NO_UNFILT_BLOOM` (`MORSEL_NO_UNFILTERED_BLOOM=1`):** Skip `build_bloom`
  when the build pipeline has no filter predicate (`pipeline_filter_shift == 0`
  and not a `Stage` source).
- **`NO_RADIX_CLONE` (`MORSEL_NO_RADIX_CLONE=1`):** Replace
  `store.mem_batches[p].clone()` (`radix_agg.rs:389`) and the immediate
  `drop(store)` (`radix_agg.rs:404`) with `std::mem::take`, and move
  per-partition build slices into worker-owned slots in `hash_join.rs:1497` so
  workers drop slices in parallel instead of single-threaded clone + drop.
  (When unset, the baseline uses the exact original borrowed
  `Arc<Vec<Vec<RecordBatch>>>` path with zero extra clones.)
- **`ASYNC_DROP` (`MORSEL_ASYNC_DROP_TABLES=1`):** Defer
  `drop(finalized_tables)` (`morsel.rs:4998`) off the query critical path via
  `spawn_blocking` (teardown deferral: the drop finishes after the runner stops
  its query clock, before process exit).
- **`FIX_BUILD_EST` (`MORSEL_Q10_FIX_BUILD_EST=1`):** Give two-sided range
  predicates on the same column (`>= AND <`) `weight = 4` (instead of `1`) and
  scale `Parquet` side estimates by projected column width (flipping `q10` to
  build filtered `orders` first).
- **`SKIP_KEY_GATHER` (`MORSEL_SKIP_KEY_GATHER=1`):** On single-key integer
  equijoins, read projected build key columns (`c_custkey == o_custkey` on
  `q13`) from the probe batch via L1-local `take` instead of 64-partition
  `gather_radix_build_column`.

Combined ablation bundles:

- **`+ALL_Q9_FIXES`:** `NO_UNFILT_BLOOM + NO_RADIX_CLONE + ASYNC_DROP`.
- **`+ALL_Q10_FIXES`:** `FIX_BUILD_EST + NO_UNFILT_BLOOM + NO_RADIX_CLONE`.
- **`+ALL_Q13_FIXES`:** `NO_UNFILT_BLOOM + NO_RADIX_CLONE + SKIP_KEY_GATHER`.
